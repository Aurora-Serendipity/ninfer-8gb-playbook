# NInfer 8 GB Playbook · 在 8 GB 笔记本显卡上跑 27B 本地大模型（v2 · KV 流式 · 两档配置）

> 一套**已实测验收**的本地大模型部署与调优方案：**NInfer v2（KV 流式）引擎 + Bonsai 2 27B 三进制量化模型 + 网关 + 控制台**，
> 跑在 **RTX 4060 Laptop（8 GB 显存 / sm_89 / Windows）** 上。
>
> **本仓库的全部数字都来自真机实测**——包括**负结果**（哪一种改法会变慢、哪一步会静默出错）和**未验项**。
> 我们不复制上游文档，只写自己量到的东西，并注明哪些结论来自上游、哪些是本机验证。
>
> **v2.0.1 = v2.0.0 + 日常档预算调整（输出 2,048 / 输入 10,240）；v2.0.0 = 从 v1（旧单 arch 引擎）迁移到 KV 流式引擎，并把配置拆成"日常 / 长上下文"两档。**
> v1 文档已归档，用 `git tag v1.0.1` 检出即可（见 [CHANGELOG](CHANGELOG.md)）。

## 这套方案能给你什么

| 能力                     | 实测结果                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **8 GB 显存跑 27B 模型** | 权重 5.52 ~ 5.94 GiB + 运行时 ⇒ 引擎起来后显存峰值 **7,015 MiB（日常）/ 7,171 MiB（长档）**，红线 7,488 MiB                                                        |
| **两档配置**             | 日常 `8g-daily`：池 **12,800** / 逻辑窗 **131,072** / 输出 **2,048** / MTP draft4；长档 `8g-longctx`：池 **51,200** / 逻辑窗 **262,144** / 输出 **8,192** / 无 MTP |
| **KV 流式（KVMem 环）**  | 设备池可远小于逻辑上下文；主机 KV 层 **3.25 GiB pinned**，四桶预算 `sum == pool` 可自证                                                                            |
| **速度**                 | 日常档 decode **63 ~ 72 tok/s**（MTP draft4）、长档 **20 tok/s**；prefill **610 ~ 697 tok/s**；TTFT（1,121 token 题面）**1.7 s**                                   |
| **长输出可达**           | 日常档配置上限 **2,048**（旧配置实测 4,096 吐满）；长档 `max_tokens=8192` 实测吐满 **8,192**（约 6 分 45 秒）                                                            |
| **长上下文检索**         | 日常档 **10,130 token** 题面中段针命中；长档 **48,062 token** 题面中段针命中（TTFT 78.7 s）                                                                        |
| **稳定性修复**           | "只服务第一条请求"已修：4 条互不相同的连续请求实测 **4/4 200**                                                                                                     |
| **开箱即用**             | 两档一键启动 / 一键停机 / 真请求体检 + 包校验 / 模型校验 / 运行中验收脚本                                                                                          |
| **踩坑记录**             | 从"出厂配方在 8 GB 卡上直接起不来"到"网关会丢超大单条历史消息"，全部留档                                                                                           |

> **一句话定位**：它不是"能跑的 demo"，而是**经过判据验收、并且知道自己在哪些地方不可靠**的一套部署。
> **8 GB 上真正可信的单题面 = 池**（日常 12,800 / 长档 51,200）；逻辑窗口更大，但超过池的部分属检索/主机层范围，
> 上游口径明确：**题面 token > 池 token ⇒ 单请求答案不可信**。

## 快速开始

```text
0) 前置：RTX 40 系（sm_89，8 GB 级）或对应 arch 的卡；驱动 ≥580；部署根目录纯 ASCII、无空格

1) 放引擎（上游分发包，三 arch 一份包）
   <部署根>\10-engine\                 ← 解压 infer-27b-kv-stream-3arch-20261019 到这一层
   本机用 engines\sm89\infer-serve.exe（801,324,544 B，sha256 3B6F9AF9…）

2) 放模型（模型不进包，需自行获取）
   <部署根>\20-model\models\bonsai2_27b_ternary_ptq1_native_mtp.ninfer
   <部署根>\10-engine\model\ 下建同名硬链接（同一份字节，零额外占用）
     cmd /c mklink /H "10-engine\model\bonsai2_27b_ternary_ptq1_native_mtp.ninfer" ^
                       "20-model\models\bonsai2_27b_ternary_ptq1_native_mtp.ninfer"

3) 打两处两档补丁（见 docs/04 附录 A；约 20 行配置改动）
   profiles.json 新增 8g-daily / 8g-longctx；launcher.py 按档注入 max-context/default-max-tokens + 网关 -u

4) 拷贝本仓库脚本到部署根
   scripts\*.bat + start-tier.ps1 / stop-tier.ps1 / healthcheck.ps1 / _common.ps1 → <部署根>\21-launchers\
   verify-engine-package.ps1 / check-model.ps1 / verify-v2-basic.ps1              → <部署根>\30-scripts\

5) 启动 + 判活（真发请求，不是探端口）
   21-launchers\start-daily.bat     ← 日常档（约 11~12 s，结尾真发一条请求）
   21-launchers\start-long.bat      ← 长档（若另一档在跑会先停掉再切）

6) 客户端填：
   Base URL : http://127.0.0.1:8081/v1     ← 网关（推荐；引擎直连是 8080）
   API Key  : 随意非空（服务端 auth disabled）
   Model    : j27b
   max_tokens: 显式给（日常 ≤2048、长档 ≤8192）
   超时     : ≥300 秒

7) 停机：21-launchers\stop-daily.bat（或 stop-long.bat），释放约 7 GB 显存
```

**判断服务是否活着，必须真发一条请求。** 只 `GET /v1/models` 返回 200 **不算数**——
上游账本记录过 worker 崩掉之后该接口照样返回 200（本方案的一键启动/体检脚本都真发请求）。
另外：**网关 8081 不实现 `GET /v1/models`（返回 501）**，判活请打引擎 8080。

## 两档怎么选（一页速查）

|                                          | 日常推荐 `8g-daily`                   | 长上下文 `8g-longctx`      |
| ---------------------------------------- | ------------------------------------- | -------------------------- |
| 适合                                     | 代码对话、日常问答、多轮、要快        | 长材料一次性喂入、单题深读 |
| 设备池（可信单题面上限）                 | **12,800**                            | **51,200**                 |
| 逻辑窗口 `--max-context`                 | **131,072**                           | **262,144**                |
| 默认输出上限                             | **2,048**                             | **8,192**                  |
| 投机解码                                 | MTP `draft_tokens=4`（accept 77~99%） | 无                         |
| 网关输入预算（推荐客户端 contextWindow） | **10,240**                             | **42,496**                 |
| 显存峰值                                 | **7,015 MiB**                         | **7,171 MiB**              |
| decode（长输出）                         | **63 ~ 72 tok/s**                     | **20 tok/s**               |
| 启动（一键脚本全链路）                   | 11 ~ 12 s                             | 11.2 s                     |

> 预算口径：网关输入预算 = 池 − 输出 − 512 slack（日常 `12800−2048−512=10240`；长档 `51200−8192−512=42496`），
> 对应上游 B35 上界"题面 + 输出 ≤ 池"。
> **档位与客户端预算必须匹配**：日常档跑着时用长档预算，最坏情况会超过池，输出可能被静默截断。

## 这套方案的适用边界（重要，先读再动手）

**适合：**

- 单张 **8 ~ 12 GB** NVIDIA 卡（sm_86 / sm_89 / sm_120a 三 arch 一份包），想跑 **长上下文 + 离线** 的大模型
- 纯文本：对话、长材料问答、代码片段工作
- **单用户、单路**：同一时刻一个请求（引擎 `--max-concurrency 1`）

**不适合：**

- **并发服务多人**：引擎单路语义，并发请求会排队（日志 `queue N ms`）
- **多模态**：模型件无视觉塔（`HAS_VISION=NO` 已实测）
- **联网/最新知识**：完全离线，知识停在训练时
- **依赖工具调用（function calling）的 agent 循环**：引擎支持但上游账本记录过不可靠（B17），
  且 agent 客户端附带的超大提示词会把本地模型压垮（见 [docs/09](docs/09-第三方客户端接入.md)）
- **把"逻辑窗口"当"可信窗口"用**：8 GB 上可信单题面 = **池**，超池必须换长档 / 分片 / 网关让位

**本方案最反直觉的几条结论：**

> 1. **出厂配方在 8 GB 卡上直接起不来**（CUDA Graph 预留 + 全局 262k 上下文），
>    必须按 [04](docs/04-8GB显存档位适配.md) 做档位适配——**这不是引擎缺陷**。
> 2. **逻辑窗口 131k/262k 不等于可信题面**：真正可信的是池（12,800 / 51,200）；
>    超池的请求引擎会打 `unverified` 告警，而**"没打警告"不等于安全**。
> 3. **网关让位是有损的**：超池时 L1 会丢弃最旧消息、L2s 会分段摘要；
>    实测**单条超大历史消息会被整条丢弃**（模型诚实回答"我没有访问任何密码"）。
>    长材料请放"最后一条用户消息"，或直接用长档 / 分片网关。

## 目录结构（部署根）

```text
<部署根目录>\
├── 10-engine\        上游三 arch 分发包（引擎 + 运行时 DLL + 启动器 + 网关 + 控制台 + 本机两档 profile）
│   ├── 启动器.bat     控制台 http://127.0.0.1:8720
│   ├── launcher.py    profiles.json 五档出厂 + 本机两档
│   ├── gateway\       网关 8081（L0~L3 让位阶梯）
│   ├── model\         模型件（与 20-model 同一份字节的硬链接）
│   └── logs\ run\     日志 / pid.json
├── 20-model\models\  模型件正本（6,394,697,216 B）
├── 21-launchers\     两档一键脚本（本仓库 scripts\ 里的 *.bat/*.ps1）
├── 30-scripts\       校验与验收脚本（本仓库 scripts\ 里的 *.ps1）
└── 40-docs\          文档与实测原始记录（可选）
```

> 启动器与脚本内部一律使用**相对路径**（`%~dp0..`），所以整个目录可以整体搬走，
> 只要保持上面这个层级关系；**部署根目录必须是纯 ASCII、无空格**。
