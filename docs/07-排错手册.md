# NInfer 本地部署 · 排错手册

> **适用配置**：RTX 4060 Laptop **8 GB**（sm_89）· NInfer sm_89 预编译引擎 · Bonsai 2 27B 三进制量化 PTQ1_0 · 端口 **8095** · OpenAI 兼容接口。
> **数字口径**：除特别标注外，本文所有数字都来自本机 2026-10-05 / 06 的实测记录与引擎日志逐字行，不是估算、不是推测。

---

## 1. 这份文档解决什么

这套部署**已经验收通过**——引擎能起、能正确回答、KVMem 长上下文机制在工作：模型名 `qwen3.8-27b`，服务地址 `http://127.0.0.1:8095/v1`，逻辑上下文 **65,536 token**，设备常驻 KV 池 **4,032 token（63 页）**，解码约 **72 token/秒**，预填约 **650 token/秒**，**同一时刻只处理 1 个请求**。但"验收通过"不等于"每次用都顺"：8 GB 显存换来的小池、单路、以及若干上游**未修缺陷**，会让它出现一些**看起来像坏了、其实是已知性质**的现象。本文就是把这些现象、它们的判据、以及**照着做就能绕过去**的办法放在一处；凡是本机没实测过的，本文不会写。

**遇到问题按这个顺序走，别跳步：**

1. **判活**（§2）——先确认服务到底是不是真的活着，这一步**必须真发一条请求**。
2. **对症状**（§3）——在速查表里找到你看到的现象。
3. **对日志**（§4）——引擎窗口的那一行才是权威读数。
4. **查缺陷与绕法**（§5）；如果是接了 agent 客户端（§6）；要对外报告（§7）。

## 2. 第一步永远是判活

### 2.1 `/v1/models` 返回 200 **不算活**

这是本部署最容易骗人的一个坑：**worker 崩了之后，`/v1/models` 照样返回 200**（上游缺陷 B02，本机没修）。端口在监听、客户端显示"已连接"，同样都只说明 HTTP 壳还在，**不说明能推理**。**只有真发一条请求才算数。**

### 2.2 三条可复制的命令（任选一条）

```powershell
# 1) 最省事：一键启动脚本，结尾它自己会真发一条请求做验证
.\21-launchers\start-engine.bat

# 2) 已经在跑、只想确认还活着：健康检查脚本（真发一条请求）
.\21-launchers\healthcheck.bat

# 3) 手工发一条（把回答原样贴出来看）
curl.exe -s http://127.0.0.1:8095/v1/chat/completions -H "Content-Type: application/json" -d "{\"model\":\"qwen3.8-27b\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply with exactly: OK\"}],\"max_tokens\":8}"
```

**判据：结果里只要出现 `"content":"OK"`，服务就是真的活着。**

### 2.3 能说明什么、不能说明什么

| 你看到的                                           | 能说明什么             | 不能说明什么             |
| -------------------------------------------------- | ---------------------- | ------------------------ |
| `GET /v1/models` 返回 200                          | 只是 HTTP 壳还活着     | **不能**说明 worker 活着 |
| 8095 端口处于监听                                  | 进程还在               | 同上                     |
| 客户端界面显示"已连接"                             | 客户端连上了 HTTP      | 同上                     |
| 引擎窗口最后一行是 `req#N done \| … \| stop token` | **真的答完了一条请求** | ——                       |

### 2.4 顺手确认另外两件事

**起服务成功的两行标志**（在标题为 `NInfer engine` 的那个窗口里）：

```text
INFO  engine ready | bonsai2-27b | total 3.3s | weights 5.94 GiB | CUDA sync auto
INFO  capacity | KV 4,032 tokens, k8v4, explicit | pages 63/1,024 | runtime 457.6 MiB | free 560.0 MiB
```

一键脚本还会打印 `[ok] the port answered after about N seconds`（本机实测约 5 秒）；已经在跑时打印 `[skip] the engine is ALREADY running`。

**停机 / 复位**：`.\21-launchers\stop-engine.bat` → 确认 → 复查三样：`none - the engine is stopped` / `port free` / `GPU memory in use now: 0 MiB`。没在跑时它会打印 `[skip] the engine is not running`。

### 2.5 判活三问（30 秒版）

| 问                           | 怎么看                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------- |
| 服务真的能推理吗？           | 发一条真请求（§2.2），看有没有 `"content":"OK"`                                   |
| 引擎自己认为刚答完过一条吗？ | 引擎窗口最后一行是 `req#N done \| … \| stop token`                                |
| 日志里有没有 §4.2 的危险行？ | 出现 `worker crash` / 超池告警 / `falling back to the tail rule` 就先按 §4.2 处理 |

三问全过还觉得不对劲，多半不是"服务坏了"，而是用法或容量问题——继续往下看。

## 3. 症状 → 处置 速查表

先做一个 10 秒分诊，能省掉一半翻表的时间：

- **一条都发不出去**（连不上、一发就错、突然全 503）→ 是**服务层**问题，回 §2 判活。
- **发得出去，但结果不对**（半截、说"材料里没有"、答得像但数字错）→ 是**用法 / 容量**问题，重点看 §5.2 里的 B01、B05、B07、B08。
- **发得出去，但慢得离谱或零输出**（一直转圈、被掐断、客户端塞了几百个工具）→ 先看日志里那条请求的 `tools` 与 `prompt`，多半是 §6。
- **压根起不来**（reservation / FATAL）→ 直接跳 §5.3。

| 症状                                                             | 最可能原因                                     | 怎么办                                                                              |
| ---------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| 客户端连不上 / 连接被拒绝                                        | 引擎没起，或地址写错                           | 跑 `21-launchers\start-engine.bat`；确认地址是 `http://127.0.0.1:8095/v1`           |
| 界面显示"已连接"，一发就错                                       | `/v1/models` 的 200 骗人（B02）                | 用 `healthcheck.bat` 真发一条；不行就重启                                           |
| **突然全部 503**                                                 | **引擎 worker 崩了**（B01）                    | `stop-engine.bat` → `start-engine.bat`；把 `max_tokens` 压到 ≤2,048                 |
| 只有一个会话一直 500（其他会话正常）                             | B03：MTP + 长预填被打断                        | 该会话已坏，**开新会话**，别在里面继续                                              |
| 请求一直"转圈"（第一轮）                                         | 冷预填，材料长                                 | 正常。10,000 token ≈ 15 秒；客户端超时设 ≥300 秒                                    |
| 第一次回答 1~2 分钟后被掐断                                      | 冷预填被连接层掐（根因未定位）                 | 客户端超时 ≥300 秒；材料分块                                                        |
| 回答半截 / 代码没写完                                            | `max_tokens` 用完                              | 显式给 2,048（必要时 4,032）；要求分段输出；看 `finish_reason`（`length` = 被截断） |
| 它说"材料里没有这一段"                                           | 材料超池，中段没被检索到                       | 分块；**把最后一条提问改短**；要求它引用原文；换个问法再问一次                      |
| 答得很像样，但数字 / 细节不对                                    | 幻觉，或内容打分失效                           | `temperature` 降到 0~0.3；要求引用原文；关键数值自己核                              |
| 越聊越慢                                                         | 上下文累积                                     | **一个任务一个会话**，开新会话                                                      |
| 越聊越啰嗦 / 复读                                                | 无重复惩罚 + 上下文污染                        | 降低 `temperature`；开新会话                                                        |
| 长会话里开始"复读计划、不干活"                                   | 思考循环（**只在开了思考时**）                 | 保持 `reasoning_effort=none`；开新会话                                              |
| 引擎起不来，报 reservation / FATAL                               | 显存不够                                       | 关掉游戏 / 绘图 / 其他推理程序，再启动                                              |
| 端口被占                                                         | 已有实例在跑                                   | `stop-engine.bat`（它会先打印占用进程明细）                                         |
| 输出里有奇怪符号 / 半句话                                        | 跨页缝截断（上游已知未修）                     | 换一种问法重问一次                                                                  |
| 接 agent 客户端后，问一句"你好"也要等 1~2 分钟、最后什么都没出来 | 客户端把**大量工具定义 + 系统提示词**一起发来  | 看 `req#N` 的 `tools` 与 `prompt` 两个数字；改用轻量模式，见 §6                     |
| 日志里几百行 `KEPT` / `SELECT` / `mask hidden` 重复出现          | **分块记账**：每 1,024 token 一块，各打印一遍  | **无视**，不是报错                                                                  |
| 日志末尾 `HTTP 499` / `client disconnected`                      | **客户端**先放弃或超时了                       | 缩小提示词、或加长客户端超时；引擎本身没事                                          |
| 想"把设备池调大一点会不会更好"                                   | 已实测是**负优化**                             | 保持 `--kv-capacity 4032`；实测数据见 §5.2                                          |
| 首次启动卡了约 90 秒才起来                                       | 显卡自适应档校准（实测约 94 秒）               | 正常，只发生在第一次；之后启动秒进                                                  |
| 启动被拒绝，提示要 Q8_G32 / row-split                            | `--lm-head-q4` / `--embedding-q4` 本制品不支持 | 去掉这两个开关（它们要求权重里 `text/output_head` 是 row-split Q8_G32）             |

## 4. 日志怎么读

主日志就是标题为 **`NInfer engine`** 的那个控制台窗口（关掉它 = 停掉引擎）。它同时会被引擎占住，用普通方式去读文件可能读到空——**直接看窗口**。

### 4.1 正常关键行（正常就该有）

| 行（逐字样例）                                                                                               | 含义                                                                        |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `INFO  engine ready \| bonsai2-27b \| total 3.3s \| weights 5.94 GiB \| CUDA sync auto`                      | 引擎起来了                                                                  |
| `INFO  capacity \| KV 4,032 tokens, k8v4, explicit \| pages 63/1,024 \| runtime 457.6 MiB \| free 560.0 MiB` | 容量与显存账：设备池 4,032 token = 63 页，以及运行时余量                    |
| `[ring] content scoring ON by default`                                                                       | 内容打分（按内容挑页）已启用                                                |
| `[ninfer] reuse host-backed: on`                                                                             | 前缀复用门控已开                                                            |
| `kvmem_score: SELECT …`                                                                                      | 检索真的在按内容选页——**只有短问题才有意义**，且**行数 > 0 才算这条路在跑** |
| `[ninfer] adopt host-backed: frontier=4523 need=71 usable=63 host_backed=17`                                 | 复用被真正采纳（样例为本机实测的一行）                                      |
| `req#N done \| … \| prompt … \| output … \| TTFT … \| prefill … tok/s \| decode … tok/s`                     | **一条请求的权威读数**——性能结论只看这一行                                  |

### 4.2 危险行（要处理）

| 行                                                                   | 含义                                           | 怎么办                                                         |
| -------------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| `FATAL …` / `ERROR engine init`                                      | 启动失败                                       | 看它打印的确切数字；多半是显存不够                             |
| `worker crash: Paged KV reservation invariant was violated`          | **引擎 worker 已死，此后所有请求 503**         | 停 → 起；把客户端 `max_tokens` 降到 ≤2,048                     |
| `prompt exceeds the resident Device KV pool …`                       | 本条请求超池（中段可能静默消失，且**不报错**） | 分块；最后一条提问写短；**这条回答不能当作"它读过全文"的证据** |
| `query span … not usable … falling back to the tail rule` + `KEPT 0` | 最后一条消息 >256 token，内容打分**整体失效**  | 长材料放前面、提问写短（见 B05）                               |
| `kvmem_score: SELECT` **行数 = 0**                                   | 内容打分没跑、退回词法排序                     | 小池下会**静默答错**（答得很像样但是错的）；别把这次答案当准   |
| `HTTP 499` / `client disconnected`                                   | 客户端先放弃了（引擎可能还在算）               | 缩小提示词、或加长客户端超时                                   |
| 同一个 `req#N` 的 `tools` 数字很大（几十 ~ 几百）                    | 客户端把一大堆工具定义发了过来                 | 见 §6                                                          |

### 4.3 吓人但无害的行（不用管）

| 行                                                    | 为什么不用管                                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `demote-other short: freed=0 …`                       | 正常的换页记账                                                                                   |
| `publish host-backed: …`                              | 无条件行为，**不代表复用生效**（要看 `adopt` 行）                                                |
| `mask hidden: …`                                      | 正常的可见性掩码                                                                                 |
| `fused rmsnorm+rope … this chunk is NOT in the index` | 已知设计后果（B08，层 0 有一段永不入索引）                                                       |
| `throughput \| 5.0s \| …`                             | **瞬时值**，别拿它当性能结论（权威的是 `req#N done` 行）                                         |
| 几百行重复的 `KEPT` / `SELECT` / `mask hidden`        | 分块记账：每 1,024 token 一块，各打印一遍                                                        |
| 新会话起标题时的一小段 `queue N ms` 与 `prompt ~127`  | 客户端用本地模型发了个起标题的小请求，正常现象                                                   |
| 首次启动的 `calibrating routes`（实测约 94 秒）       | 显卡不在引擎内置档位表里，首启校准一次；之后出现 `device profile … N routed keys` 表示复用了档位 |

### 4.4 读日志的三条纪律

1. **权威读数只有 `req#N done` 行**——`prompt` / `output` / `cache` / `TTFT` / `prefill` / `decode` 都在这一行；`throughput` 之类的瞬时值不能当结论。
2. **`kvmem_score: SELECT` 要数行数**——**0 行 = 危险信号**（内容打分没跑、退回词法排序，小池下会静默答错）；行数 > 0 才说明"按内容挑页"这条路在工作。
3. **别把"有没有报错行"当唯一判据**——本机最伤人的几种情况（超池静默丢中段、内容打分退化、跨页缝截断、层 0 不入索引）**都不报错**：答案看起来体面，但可能漏了中段。

## 5. 已知缺陷与绕法

### 5.1 先确认启动器选对了

| 启动器                                      | 用途                 | 说明                                                                      |
| ------------------------------------------- | -------------------- | ------------------------------------------------------------------------- |
| `21-launchers\start-engine.bat`             | **日常一键启动**     | 自查重复 / 文件 / 显存 → 另开窗口跑引擎 → 轮询就绪 → **真发一条请求**验证 |
| `21-launchers\start-ptq1-mtp-8g-safety.bat` | **日常推荐**         | 比基准版多 `--recover-invariant-failures` 与 `--kv-lease-growth`，防 B01  |
| `21-launchers\start-ptq1-mtp-8g.bat`        | 原始基准版（未改动） | 仍可用；设备池同样是 4,032                                                |
| `21-launchers\start-ptq1-mtp-verbatim.bat`  | **原厂参数对照**     | 本机**必定起不来**，留着复现"起不来"长什么样                              |
| `21-launchers\stop-engine.bat`              | 一键停机             | 显示进程明细 → 确认 → 终止 → 复查进程 / 端口 / 显存                       |
| `21-launchers\healthcheck.bat`              | 判活                 | 真发一条请求，看到 `"content":"OK"` 才是活的                              |

### 5.2 缺陷清单

| 现象                                                              | 状态                                                                                                                                                                                                                                                                                  | 绕法                                                                                                                                                                                                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B01 · 超池题面 + 大输出额度 ⇒ worker 崩 ⇒ 此后全 503**          | **未修**。上游单变量对照（8 GB 卡）：`max_tokens` 钳到 2,048 活着，放行 8,192 引擎就死；本机日志里出现过 11 次 `demote-other short: freed=0 … partial=1` 前兆行，靠小租约才没越过去                                                                                                   | **`max_tokens` ≤2,048（硬上限 4,032）**；日常启动器已带 `--recover-invariant-failures` 与 `--kv-lease-growth` 两个零编译止血开关                                                                            |
| **B02 · 健康检查骗人：worker 崩了 `/v1/models` 仍返回 200**       | **未修**                                                                                                                                                                                                                                                                              | 判活一律**真发请求**（`healthcheck.bat`）；看到 `"content":"OK"` 才算活                                                                                                                                     |

| **B07 · 95k 级超长题面有"命中 0"的未定位反例**                    | **未定位**                                                                                                                                                                                                                                                                            | 材料 >20,000 token 就分块，别赌                                                                                                                                                                             |

| **冷预填被连接层掐断**：预填 >2 分钟时可能被连接层断开            | **根因未定位，已缓解**                                                                                                                                                                                                                                                                | 客户端超时 ≥300 秒；材料分块                                                                                                                                                                                |

| **思考模式（chain-of-thought）带来"绕圈 / 空交付 / 半截"退化**    | 默认关闭                                                                                                                                                                                                                                                                              | 保持 `reasoning_effort=none`。本机输出上限只有 4,032，思考 token 会吃掉正文预算，**不适合开**                                                                                                               |

### 5.3 起不来的时候，日志长什么样

原厂参数在这台 8 GB 卡上的失败是**容量对不上**，不是引擎坏了：

```text
requested Engine runtime reservation requires 1863978752 bytes,
but only 1027604480 bytes are available for runtime capacity
```

即"引擎要 1.86 GB 运行显存，这张卡只剩 1.02 GB"。上游把这类失败专门命名为 **"档位适配，不是引擎缺陷"**——是配置和显卡不匹配。

本机按上游处方改了 **6 个容量数字**（没动任何调优旋钮）才塞下：

| 参数                   | 原厂值 | 本机值    | 为什么                                            |
| ---------------------- | ------ | --------- | ------------------------------------------------- |
| `--kv-capacity`        | 17920  | **4032**  | 实测的最小设备池（63 页）                         |
| `--host-kv-mib`        | 16384  | **4096**  | 要求"池与宿主层压到最小"                          |
| `--max-context`        | 262144 | **65536** | 保证"宿主页 + 设备页 ≥ 逻辑上下文页"              |
| `--default-max-tokens` | 32768  | **2048**  | 硬规矩：输出上限必须 ≤ 池大小                     |
| `--gdn-state-fp16`     | 无     | **加上**  | 小显存省内存开关（约 −130 MiB）                   |
| `--no-cuda-graph`      | 无     | **加上**  | **实测关键**：CUDA Graph 的显存预留是塞不下的主因 |

另外两个"省显存大招"**本制品直接拒绝启动**：`--lm-head-q4`、`--embedding-q4`（它们要求权重里 `text/output_head` 是 row-split Q8_G32）——报错是正常的，不是你的环境坏了。

### 5.4 哪些参数不要动

- **别把参数改回原厂**：改了起不来（想复现"起不来"就跑 `start-ptq1-mtp-verbatim.bat`）。
- **保持原厂的**：`--kv-dtype k8v4`、`--max-concurrency 1`、`--max-shared-prefixes 0`（防"逐字节重发打砖"）、`--spec mtp`、`--draft-tokens 4`、`--default-reasoning-effort none`、`--prefill-chunk 1024`。
- **别再把池压小**：4,032 token（63 页）就是实测下限，更小的池**没有测过**，会摊薄每轮可搬回的页数。
- **别自己调参去追性能**：与参考机的速度差距是 8 GB 卡的必然结果；prefill 差 3 倍以上属于该上报的范畴（§7.2）。

## 6. 接第三方 agent 客户端时的故障

### 6.1 机制（一句话）

**agent 客户端把大量工具定义（外加系统提示词）一起发来 ⇒ 提示词暴涨 ⇒ 引擎长时间预填、零输出 ⇒ 客户端等不到第一个字就先超时断开。**

### 6.2 一次性实测现场

| 项                       | 实测值                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------ |
| 你输入的内容             | "你好"（几个 token）                                                                 |
| **引擎实际收到的提示词** | **58,941 token（921 页）**                                                           |
| 客户端一起发来的工具定义 | **`tools 176`**（工具 JSON 本身 189,876 字节 ≈ 47k token；系统提示词另 14,297 字节） |
| 设备池                   | 4,032 token（63 页）⇒ **超池 14.6 倍**                                               |
| 引擎"读题"花了多久       | **98 秒**（日志 `total 1m 38.4s`），期间**一个字都不输出**                           |
| 结局                     | `cancelled` / `output 0` / `HTTP 499 client disconnected` —— **客户端先放弃了**      |

176 个工具从哪来：内置模式自带的 **27** + 全局挂载的 5 个 MCP 服务器 **135**（chrome-devtools 30 / context7 2 / firecrawl 29 / gitee 25 / github 49）+ 宿主层实验包 **14** = **176**。全局挂载的 MCP 换轻量模式也会跟进来。

### 6.3 判据：只看引擎日志里同一个 `req#N` 的两行

```text
INFO  req#2 started | openai-chat stream | 10 messages | max output 2,048 | thinking off | tools 5
INFO  req#2 done    | openai-chat | stop token | prompt 2,140 | output 29 | cache 0 (0.0%) | TTFT 3.7s | total 4.3s | prefill 586.9 tok/s | stop token
```

- `started` 行的 **`tools N`** = 客户端这次塞了多少个工具定义；
- `done` 行的 **`prompt N`** = 引擎实际要读多少 token（这就是"读题"的工作量）。

两行用同一个 `req#N` 对上。**这两个数字一大，就不是引擎坏了，是客户端的壳子太大。**

### 6.4 阈值表

| `prompt`     | `tools` | 预期                                                  |
| ------------ | ------- | ----------------------------------------------------- |
| 几百 ~ 几千  | ≤ 10    | ✅ 顺畅（实测一条 127 token 的请求 **678 毫秒**答完） |
| 1 万 ~ 3 万  | 任意    | ⚠️ 要等 20~60 秒                                      |
| **5 万以上** | 任意    | ❌ 要等 1~2 分钟，**客户端多半先超时**                |

### 6.5 对策与验收判据

1. **不要把本地模型设成 agent 客户端的默认模型**——云端那个是百万级上下文，本地是 65,536，同一个壳子饭量差 15 倍。
2. **用客户端的"本地小模型"轻量模式**：一句话人设 + 只给 5 个工具（`pwsh` + `read` / `write` / `edit` / `read_image`），不挂技能目录、不挂子智能体、不挂 MCP。
3. **唯一的全局开关**：客户端 GUI 侧边栏 Plugins 页里的两个可选实验包（`@deepseek-ai/dsh-experimental-agent-team-profile`、`@deepseek-ai/dsh-experimental-schedule-bundle`）。**关着** = 本地模型才压得进池（实测 `tools 5` / `prompt 2,140`）；**开着** = 完整云端能力（实测 `tools 18` / `prompt 5,004`，重新超池、引擎会发超池警告）。切换是热重载的，点一下即生效。
4. **一定新开会话**：把一个云端的长会话切成这个模式 = 把几万 token 的历史塞进 4k 池，又慢又超池，答案还不可信。
5. **本地模型只适合"纯聊天"用法**，不适合 agent 循环：工具调用本身有上游已知 bug（B17），壳子成本也太高。
6. **验收判据**：引擎日志那行满足 **`tools` ≤ 8 且 `prompt` ≤ 3,000**。

### 6.6 故障 → 修复的前后对照

| 观测点           | 故障时                         | 轻量模式生效后        |
| ---------------- | ------------------------------ | --------------------- |
| 工具定义个数     | `tools 176`                    | `tools 5`             |
| 工具 JSON 体积   | 189,876 字节 ≈ 47k token       | 6,162 字节            |
| 引擎收到的提示词 | 58,941 token（921 页，超池）   | 2,076 ~ 2,140 token   |
| 首个字的时间     | **98 秒，且一个字都没出**      | TTFT 3.5 ~ 3.7 秒     |
| 结局             | `HTTP 499 client disconnected` | `stop token` 正常答完 |
| 是否超池告警     | 有                             | 无                    |

合计：工具 176→5，prompt 58,941→2,076（**−96.5%**）。（中途一次读数是 `tools 18` / 16,501 字节 / `prompt 5,004`，那两个包开着时的状态。）

## 7. 报告问题时该带什么

### 7.1 必带清单

| #   | 要带的东西                       | 具体是什么                                                                                                                                          |
| --- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **硬件**                         | 显卡型号 + 显存（本机 8188 MiB，可用约 7956 MiB）、系统内存（32 GB）                                                                                |
| 2   | **引擎与模型身份**               | 引擎包名、引擎 exe 名（`ninfer-serve-89.exe`）、模型文件名（`bonsai2_27b_ternary_ptq1_native_mtp.ninfer`）                                          |
| 3   | **完整启动参数（逐字 argv）**    | 尤其是**三个池数**：`--kv-capacity` / `--max-context` / `--host-kv-mib`，以及实际打印出来的 `pages N/M` 与 `runtime` / `free`                       |
| 4   | **引擎窗口日志（逐字复制）**     | 不要改写、不要只抄半句。至少含 `engine ready` 行、`capacity \|` 行、超池告警行、**全部 `kvmem_score: SELECT` 行**、任何 `FATAL` / `worker crash` 行 |
| 5   | **`kvmem_score: SELECT` 的行数** | **0 行是危险信号**：内容打分没跑、退回词法排序，小池下会静默答错                                                                                    |
| 6   | **出问题那条请求的两行**         | 同一个 `req#N` 的 `started` 行（看 `tools`）与 `done` 行（看 `prompt` / `output` / `TTFT` / `decode`）                                              |
| 7   | **客户端侧参数**                 | 客户端名称、`max_tokens`、`temperature`、是否流式、超时设置                                                                                         |
| 8   | **题面规模**                     | 最后一条用户消息多少 token；整条 prompt 多少 token（看 `usage.prompt_tokens` 或 `done` 行的 `prompt`）                                              |
| 9   | **复现步骤**                     | 做了什么 / 期望什么 / 实际什么 / 发生几次 / 是不是每次都发生                                                                                        |
| 10  | **当时的实例状态**               | 之前是否刚出现过"全部 503"；是同一个实例还是刚重启过                                                                                                |
| 11  | **已经试过什么**                 | 试过哪些绕法、结果如何（避免重复排查）                                                                                                              |

### 7.2 口径提醒（否则报告会被打回）

- **性能结论只看 `req#N done` 行**；`throughput | 5.0s | …` 是瞬时值，不能当结论。
- **上游门槛：prefill 相对参考机差 3 倍以上就要上报。** 本机实测差 3.6 倍，属于"该交回发布方"的范畴——**不要自己继续调参**，也不要用推断代替实测、不要把长测当验收。
- **先说清是"已知缺陷"还是"新问题"。** B01 / B02 / B03 / B05 / B07 / B08、跨页缝截断、冷预填被掐都是**已知**的；附上编号能省一轮往返。
- **附上你自己的配置状态**（服务端参数、客户端参数、是否开了思考、是否接了 agent 客户端）——同一个症状在不同配置下根因不同，例如"全部 503"既可能来自 B01，也可能来自另一个实例端口冲突。

### 7.3 最小可复制报告模板

```text
【卡 / 显存】RTX 4060 Laptop 8 GB（sm_89）
【引擎 / 模型】引擎包名 + ninfer-serve-89.exe + 模型文件名
【启动参数】逐字 argv（含 --kv-capacity / --max-context / --host-kv-mib 三个池数）
【起服务两行】engine ready 行 + capacity 行（逐字）
【出问题的请求】req#N started 行 + req#N done 行（逐字，同一个 N）
【危险行】超池告警 / worker crash / falling back to the tail rule —— 有几行、逐字
【SELECT 行数】N 行（0 行请特别标注）
【客户端】名称 / max_tokens / temperature / stream / 超时
【题面规模】最后一条消息 N token；整条 prompt N token
【复现】做了什么 → 期望 → 实际 → 几次里发生几次
【已试过】绕法 1、绕法 2 …… 各自结果
```

**一句话**：能逐字就别转述——日志里一个字的差别，就可能是"已知缺陷"和"新问题"的分界。
