# 01 · 方案总览

> 这篇是入口。看完它你应该能回答三个问题：**这套东西是什么、它能干什么、它不能干什么。**

---

## 1. 一句话

**在一张 8 GB 显存的笔记本显卡上，把 27B 参数的三进制量化模型跑成"可用的本地长上下文助手"。**

"可用"的定义不是"能启动"，而是：

- 能起（`engine ready` + 容量行）
- 能答对（数数字判据通过）
- 能复用（同会话第二轮命中 99%）
- 能长时间对话而不丢中间内容（有判据与负控）
- **知道自己在哪会坏**（缺陷清单与绕法）

---

## 2. 这套方案的三个组成部分

| 部分       | 是什么                                                                    | 本仓库提供什么                                 |
| ---------- | ------------------------------------------------------------------------- | ---------------------------------------------- |
| **引擎**   | NInfer（`ninfer-serve-89.exe`），sm_89 预编译，提供 OpenAI 兼容 HTTP 接口 | 完整的启动参数、判据、适配结论；**不含二进制** |
| **模型**   | Bonsai 2 27B 三进制量化件（PTQ1_0 档，6.4 GB，自带 MTP 头）               | 校验方法、组件探测结论；**不含权重**           |
| **适配层** | 让这两样在 8 GB 卡上真正跑起来的那一堆参数、开关、脚本与判据              | **全部内容**（本仓库主体）                     |

> **关键认知**：这个项目的价值不在"下载模型然后双击"，而在**第三层**——
> 出厂参数在这张卡上**起不来**，必须做"档位适配"；而适配的每一步都有代价，
> 本仓库把每一步的**依据、实测结果和代价**都写清楚了。

## 3. 方案包含什么（清单）

### 3.1 参数适配（8 GB 档位）

| 项                             | 出厂     | 本方案     | 为什么                                                  |
| ------------------------------ | -------- | ---------- | ------------------------------------------------------- |
| `--max-context`                | 262,144  | **65,536** | KV 显存按上下文线性增长，262k 装不下                    |
| `--kv-capacity`（设备 KV 池）  | 出厂更大 | **4,032**  | 8 GB 卡的实测平衡点；**再大反而变慢**（见 §5）          |
| `--host-kv-mib`（主机 KV 层）  | 16,384   | **4,096**  | 主机层钉在内存里，按 32 GB 机器取值                     |
| `--default-max-tokens`         | 32,768   | **2,048**  | **安全红线**：客户端输出额度必须 ≤ 设备池，否则会崩引擎 |
| `--gdn-state-fp16`             | 关       | **开**     | 状态用 fp16 省显存                                      |
| `--no-cuda-graph`              | 关       | **开**     | CUDA Graph 预留显存装不下；**速度代价实测为 0**         |
| `--recover-invariant-failures` | 关       | **开**     | 零编译止血：不变量失败时救回而不是变僵尸                |
| `--kv-lease-growth`            | 关       | **开**     | 零编译止血：输出租约按需增长                            |

细节与依据：[04 · 8 GB 档位适配](04-8GB显存档位适配.md)。

### 3.2 稳定性方案

出厂启动器**没有**用到引擎自带的两个止血开关。本方案把它们打开，
用来对付本机最危险的一个缺陷：

> **超池题面 + 大输出额度 ⇒ worker 崩溃 ⇒ 此后该实例所有请求 503**（上游账本 B01）

配合的还有一条**客户端侧纪律**：`max_tokens ≤ 2,048`（硬上限 4,032）。

### 3.3 判据与验收

不靠"感觉能跑"，靠**能变红的判据**：

| 判据           | 通过标准                                                                               |
| -------------- | -------------------------------------------------------------------------------------- |
| 能力探针       | `7*5` → `35`，追加 `+2` → `37`                                                         |
| 端到端验收脚本 | `RESULT: PASS`（含超池告警的**正控与负控成对**、中段针 3/3、末尾针 2/2、不变量违规 0） |
| 包完整性       | 清单 18 条：`0 mismatched`、`0 missing`                                                |
| 模型件自检     | `MODELCHECK_VERDICT=PASS`、`LENGTH_MATCH=YES`                                          |
| 复用           | 第二轮 `cache ≥ 90%` 且 TTFT 百毫秒级                                                  |
| 不变量         | 日志 0 行违规                                                                          |

原始读数与复现命令：[05 · 实测数据与验收](05-实测数据与验收.md)。

### 3.4 工具与文档

- **一键脚本**：启动（自带检查 + 真请求验证）、停机（显示进程 + 复查端口/显存）、体检
- **三个档位启动器**：推荐版 / 基准版 / 出厂参数对照版
- **校验脚本**：档位验收、清单校验、模型件检查（均为上游脚本的本机适配版）
- **文档七篇**：从零基础入门到排错手册

## 4. 实测能力边界

| 项目       | 实测值                | 含义                           |
| ---------- | --------------------- | ------------------------------ |
| 上下文窗口 | 65,536 token          | 提问 + 回答**一起算**          |
| 设备 KV 池 | 4,032 token           | 超出后进"超池"路径，可靠性下降 |
| 主机 KV 层 | 4 GiB（钉住）         | 放不下的 KV 挪到内存           |
| 解码速度   | 72 ~ 78 token/s          | 写 1,000 字约 14 秒            |
| 预填速度   | 550 ~ 672 token/s         | 读 1,000 token 约 1.5 秒       |
| 并发       | 1（单路）             | 同一时刻只服务一个请求         |
| 模态       | 纯文本                | 无视觉塔                       |
| 显存占用   | 6,731 MiB / 8,188 MiB | 跑引擎时别开游戏               |
| 知识       | 离线                  | 不知道训练之后的事             |

## 5. 三条"反直觉但实测"的结论

### 5.1 池调大反而慢（已验证并回退）

设备池 4,032 → 8,192：解码 **−38%**、整轮 **+50%**、冷 TTFT **+43%**，正确性无提升。
原因：池变大 ⇒ 每个 token 要过更多常驻页与掩码。**上游文档里"池大更好"的对照来自另一台机、另一种形状。**

### 5.2 出厂参数在这张卡上起不来，但"不能起"不是引擎有缺陷

是**档位不适配**：权重 + 运行时 + CUDA Graph 预留超了 8 GB。
解决办法是"适配"而不是"换引擎"。

### 5.3 最危险的失败不是"报错"，是"静默答错"

| 现象                                        | 危险点                                                         |
| ------------------------------------------- | -------------------------------------------------------------- |
| 超池题面的中段可能**静默丢失**              | HTTP 200、`finish_reason=stop`、日志零告警，答案却漏了中间内容 |
| worker 崩了之后 `/v1/models` **仍返回 200** | 健康检查骗人，必须真发请求                                     |
| 最后一条消息超过 256 token                  | "按内容检索"整条链路**静默退化**为只看结尾                     |

因此本方案的一条核心纪律：**任何"看起来正常"都不能当证据，必须有判据。**

## 6. 现在这台机器上的最终配置（一页可抄）

```text
启动   ： 21-launchers\start-engine.bat      （双击；内部调用推荐版启动器）
停机   ： 21-launchers\stop-engine.bat
体检   ： 21-launchers\healthcheck.bat

容量   ： KV 4,032 tokens / k8v4 / pages 63/1,024 / runtime 457.6 MiB / free 560.0 MiB
上下文 ： 65,536
输出   ： 服务端默认 2,048；客户端硬上限 4,032
开关   ： 6 个 NINFER_* 环境变量 + --max-shared-prefixes 0 + --gdn-state-fp16
         + --no-cuda-graph + --recover-invariant-failures + --kv-lease-growth
精度   ： decode 72 ~ 78 tok/s · prefill 550 ~ 672 tok/s · TTFT 1.7 s · MTP 88.6%
KVMem  ： content scoring ON · SELECT 有 · adopt host-backed 有 · 第二轮 cache 99.0%
已知界 ： 单路 · 纯文本 · 离线 · 上下文 65,536（出厂 262,144）
```
