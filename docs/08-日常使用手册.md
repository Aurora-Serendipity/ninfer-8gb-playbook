# 日常使用手册 · 在 8 GB 笔记本上跑本地大模型

> **这台机器上跑的是什么**：RTX 4060 Laptop（显存 **8 GB** / 系统内存 **32 GB**）+ 一个 **27B 三进制量化**模型，
> 对外是一个 **OpenAI 兼容接口**：`http://127.0.0.1:8095/v1`。
> **要记住的实测值**：上下文 **65,536 token** · 设备 KV 池 **4,032 token** · 解码 **约 72 token/秒** · 首字（TTFT）**约 1.7 秒**（长材料更久）· **同一时刻只服务 1 个请求**。这份手册写给第一次用本地模型的你，照着做就行。
> **你平时只跟三层打交道**：`21-launchers\`（一键脚本）· `20-model\`（模型文件）· `10-engine\`（引擎）。
> **数字口径**：除特别标注外，全部来自 2026-10-05/06 在本机的实测。

## 2. 零基础入门

### 2.1 三句话讲清「本地模型是什么」

1. **它不是网页版的 ChatGPT。** 它是一个**跑在你自己笔记本显卡上的小型 AI**：
   **断网能用、你的文字不出本机、不按次收费**。代价是——它比云端的大模型**笨、也慢**。
2. **这台机器里装了三样东西：**
   - **模型**：`20-model\` 里那个约 **6.4 GB** 的文件，相当于「大脑」，是死的；
   - **引擎**：`10-engine\` 里的 exe，相当于「播放器」，负责让大脑动起来；
   - **服务**：端口 **8095**，把上面两样变成一个**可以连的网址**，你的客户端连的就是它。
3. **你平时只跟「服务」打交道**：开机 → 客户端连上去 → 像聊天一样用 → 关机。

### 2.2 一个类比：它像一个住在你电脑里的打字员

| 它的特点                | 生活里的对应                                       |
| ----------------------- | -------------------------------------------------- |
| 断网也能答              | 他就坐在你旁边，不需要上网查                       |
| 你的文字不出本机        | 你跟他说的话不会传到外面                           |
| 他不知道今天发生的事    | 他的知识停在「被训练的那一天」，**没有联网**       |
| 一次只服务你一个人      | **同一时刻只能处理一个请求**，别开两个客户端同时发 |
| 打字速度约 **72 字/秒** | 写 1,000 字大约要 **14 秒**                        |
| 一口气能读 **6.5 万字** | 再多就装不下，会开始「忘掉中间」                   |
| 偶尔会一本正经地编      | 这叫「幻觉」，**关键信息必须自己核对**             |

### 2.3 完整使用流程（五步）

#### 第一步 · 启动（双击）

```
21-launchers\start-engine.bat
```

- 会弹出**两个**窗口：你双击的这个（显示检查过程），以及一个标题为 **`NInfer engine`** 的窗口
  —— **后者才是引擎的日志窗口，运行期间别关它**（关掉它 = 停掉引擎）。
- 看到 `[ok] the port answered after about N seconds`，并且下面出现含 `"content":"OK"` 的一行 = 成功。
- 引擎运行占约 **6.7 GB 显存**（这张卡一共 8.2 GB）；**启动前先关掉游戏 / 绘图 / 其他 AI 程序**，否则会因为显存不够起不来（报 reservation / FATAL）。
- 启动脚本会**自己检查三件事**：是否已在运行（避免开两份）、引擎/模型文件在不在、显卡当前占用多少。
- **第一次启动**会做一次显卡自适应校准（约 **94 秒**），之后就秒起。这只是一份用户缓存，不是系统配置。

#### 第二步 · 把客户端连上去（只需做一次）

打开你的客户端（Chatbox / Cherry Studio / 任何支持 OpenAI 接口的都行），新建「自定义提供商」，填：

| 填哪一项            | 填什么                                                       |
| ------------------- | ------------------------------------------------------------ |
| 接口地址 / Base URL | `http://127.0.0.1:8095/v1`                                   |
| API Key / 密钥      | 随便填几个字，比如 `local`（服务端**没有鉴权**，但不能留空） |
| 模型名 / Model      | `qwen3.8-27b`                                                |
| 超时时间 / Timeout  | **≥300 秒**（长材料第一次回答可能要几十秒到几分钟）          |
| 流式输出 / Stream   | **打开**（否则长回答期间界面像卡住）                         |

> ⚠️ **不要把它改成 `0.0.0.0`，也不要给别的机器用**——这个服务**没有鉴权**，只在 `127.0.0.1` 上听。

#### 第三步 · 开始用

见第 4 节「三种用法的标准姿势」和第 5 节「四个真实场景」。

#### 第四步 · 关机（双击）

```
21-launchers\stop-engine.bat
```

- 按 `Y` 确认（不按的话 **10 秒后自动确认**）。
- 成功标志：出现 `[check] process after stop: none` + `GPU memory in use now: 0 MiB`。
- 它会显示停掉了哪个进程，并复查端口与显存。

#### 第五步 · 出问题了

先跑一下 **`21-launchers\healthcheck.bat`**，看到 `"content":"OK"` 就是活着。常见症状：

| 症状                               | 最可能的原因                     | 怎么办                                                                |
| ---------------------------------- | -------------------------------- | --------------------------------------------------------------------- |
| 客户端连不上                       | 引擎没起 / 地址写错              | 跑 `start-engine.bat`；确认地址是 `http://127.0.0.1:8095/v1`          |
| 请求一直「转圈」                   | 首轮冷预填（材料长）             | 正常。10,000 token ≈ **15 秒**；客户端超时设 ≥300 秒                  |
| **突然全部 503**                   | **引擎 worker 崩了**（上游 B01） | `stop-engine.bat` → `start-engine.bat`；并把 `max_tokens` 压到 ≤2,048 |
| 界面显示「已连接」但一发就错       | `/v1/models` 的 200 骗人（B02）  | 用 `healthcheck.bat` 真发一条；不行就重启                             |
| 回答半截                           | `max_tokens` 用完                | 提高 `max_tokens`；要求分段输出；看 `finish_reason`                   |
| 它说「材料里没有」                 | 材料超池、中段没被检索到         | 分块；**把最后一条提问改短**；要求引用原文                            |
| 第一次回答 1~2 分钟后被掐断        | 冷预填被连接层掐（根因未定位）   | 客户端超时 ≥300 秒；材料分块                                          |
| 越聊越慢                           | 上下文累积                       | 开新会话                                                              |
| 引擎起不来，报 reservation / FATAL | 显存不够                         | 关掉游戏/绘图/其他推理程序，再启动                                    |

## 3. 能力边界（先知道「不行」什么，省得白折腾）

| 项目                         | 实际值                                                      | 你要知道什么                                                          |
| ---------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------- |
| **上下文**                   | **65,536 token**（提问 + 回答**一起算**）                   | 出厂是 262,144，为塞进 8 GB 显存压到了 1/4。**超了会被拒**，不是 bug  |
| **单次输出上限**             | 服务端默认 **2,048**；客户端最多可要到 **4,032**            | 超过**设备池** 4,032 会把引擎搞崩（上游 B01）。**2,048 是实测安全值** |
| 速度（解码）                 | **约 72 token/秒**                                          | 1,000 token ≈ **14 秒**。这是 8 GB 卡的必然，不是装坏了               |
| 速度（预填）                 | **约 650 token/秒**                                         | 1,000 token 材料 ≈ **1.5 秒**；10,000 token ≈ **15 秒**               |
| **首字延迟（TTFT）**         | **约 1.7 秒**                                               | 材料越长首答越久；冷预填被掐断的风险也越大                            |
| **并发**                     | **同一时刻只处理 1 个请求**                                 | 别在多个客户端同时发；第二个会排队等                                  |
| 模态                         | **纯文本**                                                  | 不支持图片、不支持听声音（`modalities.vision = false`）               |
| 联网                         | **没有**                                                    | 它的知识截止在训练时；**不知道今天的 API 变更**                       |
| 工具 / 函数调用              | 引擎支持，但**上游记录过格式错乱、循环调用**（B17，未查清） | **别依赖它做工具调用**；要调用就在客户端自己解析                      |
| 思考模式（chain-of-thought） | **默认关闭**                                                | 可开，但**开了有「绕圈 / 空交付」的风险**，且会吃掉输出额度           |
| 精度                         | 27B 三进制量化                                              | 比同规模全精度模型弱；**代码能写，但必须自己验**                      |
| 显存占用                     | 引擎起来后 **6.7 GB / 8.2 GB**                              | 跑引擎时**别开游戏/绘图软件**，否则启动会报 reservation 失败          |
| 内存占用                     | 主机 KV 层钉住 **4 GiB** + 页缓存                           | 机器 32 GB，够用；但别同时跑大内存任务                                |

> **两套实测读数略有出入，不用纠结**：一份记解码 **72.1** / 预填 **551.7** / TTFT **2.1 秒**，另一份（`-safety` 启动器复测）记 **72.2** / **653.8** / **1.7 秒**，差别来自口径与启动器版本。记住「**解码约 72 字/秒、长材料首答要等**」就够。

### 一句话总结能力边界

> **它是一台「离线、单线程、72 字/秒、能读 6.5 万 token 的打字员」。**
> 适合：读你贴给它的材料、写代码片段、回答材料内的问题。
> 不适合：查最新资料、跑长任务、并行服务多人、图像、依赖工具调用。

## 4. 三种用法的标准姿势

### 4.1 纯文本对话

- 直接聊就行，服务端默认 `temperature 0.7`。
- **要点：一轮一事。** 上下文是提问和回答共享的，聊久了会变慢（每轮都要重新处理）。
- **聊跑偏了就开新会话**，不要一直往下灌。
- 想要稳定的答案（比如问事实、问定义）：把 `temperature` 调到 **0~0.3**。

### 4.2 长材料问答（本机最需要注意的场景）

**核心规则只有一条：**

> ## ★ 长材料放在前面的消息里，最后一条提问写短（≤ 256 token）

**为什么**：引擎「按内容找相关段落」（内容打分）用的是**最后一条用户消息**的 token 跨度作查询。
它一旦超过 **256 token**，内容打分就**整体失效**，退化成「只看结尾」的规则 ——
日志里会打印 `query span … not usable … falling back to the tail rule` + `KEPT 0`，**而且不报错**。
你会拿到一个很像样、但可能漏掉中段的答案。

**正确写法（分两轮）：**

```
第 1 轮（用户）：【把整份材料贴进去，不要带问题】

第 2 轮（用户）：这份材料里，XXX 是多少？（一句话的短问题）
```

**错误写法（一轮塞完）**：把【材料 + 问题】一起发 —— 材料把问题挤成一条超长消息 ⇒ 内容打分失效。

- **怎么知道材料有多少 token**：看客户端显示的计数，或看回答 JSON 里的 `usage.prompt_tokens`。**粗估**：中文 **1 字 ≈ 1 token**；英文 **4 字符 ≈ 1 token**；代码 **3~4 字符 ≈ 1 token**。
- 详细的规模策略和分块方法见第 7 节。

### 4.3 代码工作

一句话版：**贴小段、明确要求、自己验证。** 完整做法见第 8 节。

## 5. 四个真实场景，照着做

### 场景 A：问一段代码（最常见）

在客户端里**新开一个对话**，把下面模板填好发出去：

```
【语言/版本】Python 3.11
【任务】解释下面这个函数做了什么，并指出可能的边界问题
【要求】先复述你看到的三个关键变量名，再回答

<把你的代码贴在这里，控制在 300 行以内>
```

**为什么这么写：**

- 写清语言和版本 → 否则它可能按旧语法回答；
- 「先复述关键变量名」→ 这是**最便宜的「它到底读到了没」的自检**；
- 一次只贴一个文件 → 贴太多就进入「超池」状态，中间的内容可能静默丢失。

### 场景 B：贴一份长材料，问一个问题（**最需要注意**）

**必须分两轮**——这是本机最重要的一条规则：

```
第 1 轮（用户）：【把整份材料贴进去，不要带问题】

第 2 轮（用户）：这份材料里，XXX 是多少？（一句话的短问题）
```

**为什么不能一轮塞完**：引擎「按内容找相关段落」的能力，是用**你最后一条消息**去检索的。
如果那一条本身就几千字，检索会整个失效，**而且不报错** ——
它会给你一个很像样、但可能漏掉中段的答案。

**材料多大才安全**（完整版见第 7.2 节）：**≤ 3,500 token**（约 2,000 字中文 / 300 行代码）最稳，直接贴直接问；4,000 ~ 20,000 用上面的两轮法并要求**引用原文片段**；20,000 ~ 60,000 先分块做摘要再基于摘要提问；**> 60,000 不支持**，必须分块。

### 场景 C：让它写一小段代码

**最大的坑是「输出半截」**（写到一半被上限截断）。这样写：

````
【语言/版本】Python 3.11
【任务】写一个把 CSV 按指定列去重并输出统计的命令行脚本
【要求】
1. 分 2 段输出，每段用 ``` 代码块闭合，每段结束写 [SEGMENT n/2 DONE]
2. 我回复「继续」你再输出下一段
3. 不要引入第三方依赖
````

客户端里把 **`max_tokens` 设成 2048**（服务端默认就是 2048；**绝对不要超过 4032**）。

**拿到代码后先跑一遍**：模型写的代码「看起来对」的比例，远高于「真的对」。

### 场景 D：贴一段报错

给它三样东西，缺一样它就只能猜：

```
1) 完整报错栈（原样贴，不要删行）
2) 最小可复现代码
3) 环境：Python 3.11 / 依赖版本 / 操作系统

要求：先只回答「最可能的 3 个原因」，每个原因给出验证方法。不要直接给修复代码。
```

## 6. 客户端参数手册

| 参数               | 服务端默认       | 建议范围                                             | 说明                                                                    |
| ------------------ | ---------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| **`max_tokens`**   | 2,048            | **代码生成 2,048~4,032**；问答 512~1,024；聊天 1,024 | **最重要的一个**。给少了输出会半截；**给超过 4,032 有把引擎搞崩的风险** |
| `temperature`      | 0.7              | 代码/事实 **0~0.3**；聊天 0.7；头脑风暴 0.8~0.9      | 越高越发散，也越容易编                                                  |
| `top_p`            | 0.9              | 0.9                                                  | 一般不用动                                                              |
| `top_k`            | 20               | 20                                                   | 一般不用动                                                              |
| `presence_penalty` | 0                | 保持 0                                               | 上游建议思考模式下用 1.0~1.5，但**我们没开思考**，别动                  |
| `stream`           | —                | **开**                                               | 长回答时能看见进度                                                      |
| `reasoning_effort` | `none`（思考关） | **保持 none**                                        | 开了会吃掉输出额度，且触发「绕圈 / 空交付」的风险（上游 `04`）          |

**四个场景的推荐预设：**

| 场景                | temperature   | max_tokens      | 提示词要点                                   |
| ------------------- | ------------- | --------------- | -------------------------------------------- |
| 代码生成 / 重构     | **0.1 ~ 0.3** | **2,048~4,032** | 明确语言与版本；要求「只输出代码」；要求分段 |
| 代码解释 / 报错排查 | 0.2 ~ 0.4     | 1,024           | 贴最小可复现片段 + 完整报错                  |
| 长材料问答          | **0**         | 1,024           | 要求「引用原文片段」                         |
| 日常聊天            | 0.7           | 1,024           | ——                                           |

## 7. 长材料的正确做法

### 7.1 那条核心规则 + 一个自检

- **规则**：最后一条用户消息保持短（**≤256 token**）。
- **为什么**：内容打分只拿最后一条用户消息当查询；它超过 256 token 就整体失效、退化成「尾部规则」（日志打印 `query span … not usable … falling back to the tail rule` + `KEPT 0`），**而且不报错**。
- **自检**：回答里如果它说「材料里没有这段」，先别信 —— 把问题换一种问法**再问一次**；如果两次回答矛盾，就是检索没覆盖到，请分块。
- **反面信号**：日志出现 `prompt exceeds the resident Device KV pool …` 说明这一条**超池**了，**不能当成「它读过了全部材料」的证据**（中段可能静默消失）。

### 7.2 按材料规模选策略

| 材料规模                                        | 可靠性                                                                        | 建议                                               |
| ----------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------- |
| **≤ 3,500 token**（约 2,000 汉字 / 300 行代码） | **最高**——全部装在设备池里，中段不会丢                                        | 直接贴、直接问                                     |
| 4,000 ~ 20,000 token                            | 中——进入「超池」路径，靠检索搬页                                              | 严格遵守两轮写法；**要求它「引用原文片段」**再核对 |
| 20,000 ~ 60,000 token                           | 低——上游有「命中 0」的**未定位反例**（B07）；层 0 有一段**永不入索引**（B08） | 先分块做摘要，再基于摘要提问                       |
| **> 60,000 token**                              | 不支持                                                                        | 必须分块                                           |

### 7.3 分块策略

| 材料类型  | 分块单位    | 每块大小     | 做法                                                                 |
| --------- | ----------- | ------------ | -------------------------------------------------------------------- |
| 合同/文档 | 按章节      | ≤3,000 token | 每块单独一轮，问「这一章讲了什么」；最后把各轮结论合成一份再问总问题 |
| 代码库    | 按文件/模块 | ≤2,000 token | 先贴接口与调用关系，再贴具体实现                                     |
| 日志      | 按时间段    | ≤3,000 token | 只贴报错前后的窗口，不要整份                                         |
| 表格/数据 | 按表        | ≤2,000 token | 贴上表头 + 相关行                                                    |

### 7.4 会话管理

- **一轮任务一个会话**。做完就开新的（客户端里叫「新建对话」）。
- 会话越长：每轮越慢（要重新处理越来越多的上下文），且越容易丢中段。
- **同一会话里接着追问会很快**（前缀复用约 **99%**，第二轮 TTFT 约 **250 毫秒**）——
  这是正常现象，不是它在偷懒。

## 8. 代码工作专题

### 8.1 让它读代码

```text
【文件路径】src/cache/store.py
【语言/版本】Python 3.11
【任务】解释 get_or_load 的缓存淘汰逻辑，并指出可能的 bug

<代码贴这里，控制在 300 行以内>
```

**要点：**

- **一次一个文件 / 一个函数**，别一次贴十个文件（超池后中段会丢，你会得到「理直气壮的错误答案」）。
- 明确告诉它**语言与版本**，否则它可能按旧语法回答。
- 让它**先复述它看到的关键行**（「先把这段代码里的三个关键变量名列出来」）—— 这是最便宜的「它到底读到了没」的自检。

### 8.2 让它写代码（防半截）

**半截是本机最常见的失败**：输出 2,048 token 就到头，文件没写完。

1. **显式给 `max_tokens`**（别用默认值）：单文件 **2,048** 起，必要时 **4,032**。
2. **明确要求分段**：

   ````
   这是一个超过 300 行的文件。请分 3 段输出，每段用 ``` 代码块闭合，
   每段结束时写 [SEGMENT n/3 DONE]，我回复「继续」你再输出下一段。
   ````

3. **判断半截的方法**：看 `finish_reason` —— `length` = 被上限截断了（**不可用**），`stop` = 正常结束；另外**看代码围栏是否成对**（``` 的数量是否为偶数）。
4. **拿到代码先编译 / 运行一遍**。模型写的代码「看起来对」的比例远高于「真的对」。

### 8.3 代码审查 / 重构

```
任务：审查下面这个函数，输出三部分：
1. 它实际做了什么（逐行摘要）
2. 潜在的 bug 或边界问题（给出具体输入条件）
3. 重构建议（给出完整替换代码，Python 3.11）
限制：不要改变对外行为；不要引入新依赖。
```

**要点**：明确要求「**给出具体输入条件**」——
否则它会给你一堆「可能会空指针」之类的泛泛之谈。

### 8.4 报错排查

**给它三样东西**（缺一样它就只能猜）：

```text
1) 完整报错栈（原样贴，不要删行）
2) 最小可复现代码
3) 环境：Python 3.11 / 依赖版本 / 操作系统
```

然后要求：

```
先只回答「最可能的 3 个原因」，每个原因给出验证方法（一条命令或一段代码）。
不要直接给修复代码。
```

—— 先定位再修，比它一上来给你一大段改写要可靠得多。

### 8.5 代码场景的红线

| 红线                                | 原因                                                 |
| ----------------------------------- | ---------------------------------------------------- |
| **不要用它查「最新版本/最新 API」** | 无联网，知识有截止日期，它会编出看起来很合理的旧签名 |
| **不要一次喂整个代码库**            | 超池后中段静默丢失（B01/B05/B07）                    |
| **不要相信它「我读过了」的声明**    | 中段可能根本没进它的视野；让它引用原文               |
| **不要让它直接改生产文件**          | 它没有文件系统权限；而且输出可能半截                 |
| **关键数值/字符串必须自己核对**     | 例如端口号、密钥名、正则表达式 —— 抄错一位就出事     |

## 9. 新手最容易踩的坑

| #   | 坑                                    | 后果                                      | 正确做法                             |
| --- | ------------------------------------- | ----------------------------------------- | ------------------------------------ |
| 1   | 把材料塞进一条消息里问                | 检索失效，答案漏中段**还不报错**          | 长材料放前面、**提问写短**           |
| 2   | 不管 `max_tokens`                     | 输出半截                                  | 代码场景显式给 2,048；**别超 4,032** |
| 3   | 看到「能连上」就以为正常              | `/v1/models` 返回 200 也可能是坏的（B02） | **真发一条请求**才算活               |
| 4   | 一边开游戏一边启动                    | 引擎起不来（显存不够）                    | 先关 GPU 程序                        |
| 5   | 用它查「最新版本 / 最新 API」         | 它会编出看起来很合理的旧答案              | **它没有联网**，这类问题别问它       |
| 6   | 一个会话一直聊下去                    | 越聊越慢、越容易丢中段                    | **一个任务一个会话**                 |
| 7   | 逐字节重发同一条超池题面              | 有一条已知路径会把实例打砖（此后全 503）  | 别重发；开新会话重新组织材料         |
| 8   | 把本地模型设成 agent 客户端的默认模型 | 一句「你好」要等 1~2 分钟，最后什么都没有 | 见下面 9.1                           |

### 9.1 如果你用 agent 客户端（DSH 等）

agent 客户端会把**工具定义 + 系统提示词**一起发过来，本地模型扛不动这种「壳子」。一次真实故障的实测：你输入「你好」（几个 token），引擎实际收到 **58,941 token**（921 页）+ **176 个工具定义**，「读题」就花了 **98 秒**，最后 **HTTP 499 client disconnected**（客户端先放弃了）。

**怎么提前判断一个请求会不会卡**：看引擎日志里 `req#N started` 那行的 `prompt` 和 `tools` 两个数字。

| prompt       | tools | 预期                                                  |
| ------------ | ----- | ----------------------------------------------------- |
| 几百 ~ 几千  | ≤ 10  | ✅ 顺畅（实测一条 127 token 的请求 **678 毫秒**答完） |
| 1 万 ~ 3 万  | 任意  | ⚠️ 要等 20~60 秒                                      |
| **5 万以上** | 任意  | ❌ 要等 1~2 分钟，客户端多半先超时                    |

**对策**：用客户端提供的「本地小模型模式」（只带一句话人设 + 少量工具 + 自动压缩）。落地后的实测是 **`tools 5` / `prompt 2,140` / TTFT 3.7 秒**；验收判据同一个：**`tools` ≤ 8 且 `prompt` ≤ 3,000**。**不要把本地模型设成 agent 的默认模型**——同一个壳子，云端有 100 万上下文，本地只有 6.5 万。

## 11. 术语表

| 术语                            | 人话解释                                                      |
| ------------------------------- | ------------------------------------------------------------- |
| **token**                       | 模型的最小文字单位。中文约 1 字 1 个，英文约 4 字符 1 个      |
| **上下文 / context**            | 一次请求里「提问 + 回答」能容纳的 token 总数。本机 **65,536** |
| **prefill / 预填**              | 模型「读题」的阶段，本机约 **650 token/秒**                   |
| **decode / 解码**               | 模型「写字」的阶段，本机约 **72 token/秒**                    |
| **TTFT**                        | 从发请求到吐出第一个字的时间，本机约 **1.7 秒**               |
| **KV cache**                    | 模型读过的内容的「笔记」，存在显存里                          |
| **设备池 / pool**               | 显存里放笔记的位置，本机 **4,032 token**                      |
| **主机层 / host KV**            | 笔记放不下时挪到内存里的部分，本机钉住 **4 GiB**              |
| **KVMem 环**                    | 按「和当前问题最相关」把笔记搬回显存的机制                    |
| **前缀复用**                    | 同一会话第二轮不用重读前面内容，**秒回**的原因                |
| **MTP / 投机解码**              | 一次猜几个字再验，快一些的机制（本机接受率约 **88.6%**）      |
| **超池**                        | 材料比设备池大，需要搬页的状态（可靠性下降，见第 7 节）       |
| **B01 / B02 / B05 / B07 / B08** | 上游的已知缺陷编号，含义见第 8.5 节与第 9 节                  |

## 12. 可复用的部署经验（跨机器 / 跨客户端通用）

> 从"8 GB 笔记本卡跑 27B + 接 agent 客户端"这条完整链路上沉淀下来的**通用经验**，与具体版本无关。
> 每条都写成「**判据 → 动作 → 理由**」——判据必须能"变红"，否则它不叫判据。

**12.1 先量两个数，再谈模型能力。**
判据：客户端请求里附带的 `tools N` 与引擎侧收到的 `prompt N`。
动作：任何"本地模型接入"的第一次联调，**先发一句"你好"量这两个数**。
理由：实测一句"你好"被 agent 客户端包成 **58,941 token**（其中工具定义 189,876 字节）
——卡死先怀疑**客户端的壳子**，不是模型本身。

**12.2 总窗口 ≠ 单次请求能吃下的量。**
判据：`prompt` 是否超过**设备常驻 KV 池**（本方案 4,032；总窗口 65,536）。
动作：**容量决策一律以池为准**——客户端输出上限 ≤ 池、prompt 留余量、长材料分段喂。
理由：超池**不报错**，而是"中段静默丢失"（HTTP 200 + 看似合理的错答案），比卡死危险得多。

**12.3 小显存的第一性原理：先减"预留"，再谈吞吐。**
判据：起不来 + `only N bytes are available for runtime capacity` / reservation FATAL。
动作：改**容量类**参数（池大小 / host 层 / max-context / 输出上限），并**关掉 CUDA Graph 预留**。
理由：显存小时，"预留"比"速度"先杀死你；开图优化反而起不来。

**12.4 客户端不写输出上限 = 埋雷。**
判据：引擎日志 `req#N started | … | max output 32768`（远大于池）。
动作：**在客户端配置里显式写死输出上限**。
理由：适配器会兜底发一个大值（实测 32,768），正好踩中"超池 + 大输出额度 ⇒ worker 崩 ⇒ 此后全 503"；
这类崩不可自愈，而 `/v1/models` 照样返回 200（健康检查骗人）。

**12.5 排查"工具/提示词爆炸"，先问"它注册在哪一层"。**
判据：换了极简模式，工具数/提示词几乎没降。
动作：分清三种位置——**全局层**（可屏蔽）、**模式自己的层**（跟着模式走）、
**agent 自己的层**（任何"按 agent 屏蔽"都无效）。
理由：**能继承 ≠ 能删除**；只有从更外层才能关掉它。

**12.6 把"减法"做成一个开关，别靠自觉。**
判据：你能否在 30 秒内、不碰配置文件地切回完整能力？
动作：把"要不要重装备"做成 GUI 里一个**可逆开关**，并写进日常注意事项。
理由："记得手动禁用/启用"迟早会忘；做成开关后，代价与恢复路径都一目了然。

**12.7 验收标准要机器可判，而且能离线复核。**
判据：`tools ≤ N`、`prompt ≤ M`、`finish_reason=stop`、TTFT。
动作：把这几个数写进交付标准；并知道**客户端会话日志里那条"请求头记录"就是发给引擎的原文**
（工具清单、输出上限全在里面）——不看引擎窗口也能逐项复核。
理由："感觉快了"不能当交付依据。

**12.8 本地小模型的稳态：不思考 + 短输出 + 单路。**
判据：`thinking off`；输出到上限就截断；同一时刻只有一个请求。
动作：**别开思考**（思考 token 也占输出额度）、长文分次写、**别要求并行 agent / 并行工具调用**。
理由：池只有 4,032 时"思考 + 正文"装不下。

**12.9 改配置的三条铁律：备份 → 列清单确认 → 校验器 + 追加式写入。**
判据：改完还能启动，且原有内容可**逐字节比对**。
动作：先备份 → 把"完整路径 + 原值 → 新值"列给人确认 → 用校验脚本 →
**新内容追加到文件末尾**，事后比对"前 N 字节原样"。
理由：追加式 + 前缀比对是唯一能**事后证明"没动到别处"**的改法。

**12.10 ⚠️ 自动判词的脚本，必须验证"它测的就是它启动的那个对象"。**
判据：判词说"引擎没按预期报警/没答对"，但引擎窗口里那条请求根本不是你这次发的。
动作：给任何"自动验收 / 自动判词"的工具加一条守卫——**回答我的必须是我启动的那个进程**
（比对监听端口的 PID）。
理由：真实事故——验收脚本的清场逻辑写错（用 WQL 的 `=` 去配通配符，永远匹配不到进程）⇒
杀不掉残留引擎 ⇒ 本脚本自己的引擎因显存不足启动失败，而健康探测被**残留引擎**回答 200 ⇒
脚本"看起来就绪"、把请求发给了别的引擎、判词却去自己的日志里找 ⇒ **报出完全失真的判词**。

**12.11 脚本改完，先过一遍语法检查。**
判据：`文件在、文档说能用、一跑就报错`。
动作：PowerShell 用 `[Parser]::ParseFile` 过一遍；批处理至少实跑一次最简路径
（例如故意传不存在的路径，看它走不走"友好拒绝"分支）。
理由：本方案里就有一个脚本因为 `else {}` 少个语句分隔符而**从来没跑起来过**，
而文档一直写着"直接跑即可"。

**12.12 ⚠️ 别把它当计数器。**
判据：涉及数量、计数、逐项清点的回答。
动作：**这类结论一律自己核对**；它可靠的是"读材料问答""写/改代码片段"。
理由：实测给它 200 次重复文本、问某个词出现几次，它答 **30**（两轮答案一致 ⇒ 不是随机错，是能力上限）。

**12.13 参数不要凭常识调，要留对照。**
判据：任何"更大 / 更快 / 更强"的直觉型改动。
动作：**单变量 + 至少三次复测 + 与基准同口径对比**；文档里的数字换台机器一律不照用。
理由：本机把设备池从 4,032 调到 8,192，实测解码 **−38 %**、整轮 **+50 %**、冷启动 TTFT **+43 %**，
正确性毫无提升 ⇒ 已回退。**"池越大越好"是错的。**

**12.14 两份同名的上游文档 = 两个版本，别当重复文件处理。**
判据：同名、内容哈希不同、差几百字节。
动作：**先定哪份为准**（或两份都留并注明），不要当成冗余清理掉。

**12.15 文档与实物要"双向"核对。**
判据：文档里的每个路径 / 哈希 / 参数 / **操作指令**。
动作：不只读文档，还要拿它去比对实物；**操作性描述错，比数字错更危险**。
理由：一轮审计能查出几十处不一致，最危险的一条往往是"文档说日常用 A 启动器、实际该用 B"。

**12.16 改动留下的备份，验收完就清掉，并同步文档里的计数。**
判据：目录里出现 `*.bak`、0 字节日志、以及文档写死的文件总数。
动作：确认无用后**逐个绝对路径**删除（不用通配符），然后**更新文档里所有写死的数字**——
否则"清理"本身会制造新的不一致。
