# 日常使用手册 · 在 8 GB 笔记本上跑本地大模型（v2 · 两档）

> **这台机器上跑的是什么**：RTX 4060 Laptop（显存 **8 GB** / 系统内存 **32 GB**）+ 一个 **27B 三进制量化**模型
> （NInfer v2 KV 流式引擎），对外是一个 **OpenAI 兼容接口**。
>
> **要记住的实测值**：日常档池 **12,800 token** / 逻辑窗 **131,072** / 默认输出 **2,048** / 解码 **63~72 token/秒**；
> 长档池 **51,200** / 逻辑窗 **262,144** / 输出 **8,192** / 解码 **20 token/秒**；
> 首字（TTFT）**约 1.7 秒**（长材料更久）；**同一时刻只服务 1 个请求**。
> 这份手册写给第一次用本地模型的你，照着做就行。

---

## 1. 一页速查

```text
启动日常档 ： 21-launchers\start-daily.bat       （双击；约 11~12 s，结尾真发一条请求）
启动长档   ： 21-launchers\start-long.bat        （若另一档在跑会先停掉）
停机       ： 21-launchers\stop-daily.bat        （或 stop-long.bat，两档通用）
体检       ： 21-launchers\healthcheck.bat       （真发请求，末行 [PASS] 才算活）
控制台     ： 21-launchers\open-ui.bat           → http://127.0.0.1:8720

客户端     ： Base URL http://127.0.0.1:8081/v1 （网关；也可直连 8080）
             Model    j27b
             API Key  随便非空
             max_tokens 必须显式给（日常 ≤2048 / 长档 ≤8192）
             超时     ≥300 秒

铁律       ： 题面 + 输出 ≤ 池（日常 12,800 / 长档 51,200）
             一次只发一个请求（单路）
             判活必须真发请求（/v1/models 200 不算）
```

## 2. 零基础入门

### 2.1 三句话讲清「本地模型是什么」

1. 它是一个**住在你电脑里**的 AI 助手，全程离线，不联网、不花钱、不上传你的材料。
2. 它的"大脑"是 27B 参数的量化模型，塞进了 8 GB 显存的笔记本显卡里。
3. 它对外暴露一个**标准接口**（OpenAI 兼容），所以你能用各种客户端接它。

### 2.2 一个类比：它像一个住在你电脑里的打字员

- 打字员的工作台就是**设备 KV 池**（日常 12,800 token）——台面上能摊开的材料有限。
- 台面放不下的材料堆在**书架**（主机 KV，3.25 GiB）上，需要时按你问的问题去翻（检索）。
- **桌面太小、材料太多**时，他可能漏看中间几页——所以有"题面 + 输出 ≤ 池"这条铁律。
- 两个档位 = 两种工作模式：**日常档**（台面小但手快，63~72 token/s）、**长档**（台面大但手慢，20 token/s）。

### 2.3 完整使用流程（五步）

1. **确认 GPU 空闲**：`nvidia-smi` 看显存占用；跑之前关掉游戏/录屏/其它 AI 程序。
2. **启动一个档**：双击 `21-launchers\start-daily.bat`（日常）或 `start-long.bat`（长档），等结尾出现
   `[proof] content = "OK"` 与 `[done] the service is REALLY serving`。
3. **客户端填**：baseURL `http://127.0.0.1:8081/v1`、model `j27b`、key 随便非空、`max_tokens` 显式给。
4. **用**：对话 / 贴材料 / 改代码（见 §6~§10）。
5. **用完停机**：`stop-daily.bat`（或 `stop-long.bat`），释放约 7 GB 显存。

## 3. 两档怎么选、怎么切

|              | 日常推荐 `8g-daily`            | 长上下文 `8g-longctx`                                  |
| ------------ | ------------------------------ | ------------------------------------------------------ |
| 适合         | 代码对话、日常问答、多轮、要快 | 长材料一次性喂入、单题深读                             |
| 可信单题面   | **12,800** token               | **51,200** token                                       |
| 逻辑窗口     | 131,072                        | 262,144                                                |
| 默认输出     | 2,048                          | 8,192                                                  |
| 速度         | **63 ~ 72 tok/s**              | **20 tok/s**                                           |
| 长档典型耗时 | —                              | 8,192 输出 ≈ **6 分 45 秒**；48k 题面 TTFT ≈ **79 秒** |

**切换**：直接双击另一个档的启动脚本即可——脚本会先停掉当前档再起新档（不会两个同时跑）。
切换后**客户端要选对应的 provider/预算**（DSH 里是两个 provider，见 §11）。

**选档口诀**：

- 材料很短、要来回聊、要它写代码 ⇒ **日常档**
- 一份 2~5 万字的材料，想一口气问透 ⇒ **长档**（但准备好等）
- 材料超过长档池（51,200）⇒ 分片或用分段摘要（见 §9）

## 4. 四套脚本

| 脚本                               | 作用                                                                          | 成功判据                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `start-daily.bat`                  | 启动日常档：确保控制台在跑 → 预算预检 → 起引擎+网关 → 轮询就绪 → **真发请求** | 末行 `[done] the service is REALLY serving`；`engine=7421/redline=7488` |
| `start-long.bat`                   | 启动长档（同上逻辑）                                                          | 末行同上；`engine=7312/redline=7488`                                    |
| `stop-daily.bat` / `stop-long.bat` | 停止引擎与网关（**只停 launcher 记录的进程**）                                | `[done] the engine is stopped.`；端口 8080/8081 都不在听                |
| `healthcheck.bat`                  | 真发一条请求判活                                                              | 末行 `[PASS ] the engine is really serving`                             |
| `open-ui.bat`                      | 打开控制台 8720（没跑就先拉起）                                               | 浏览器打开 `http://127.0.0.1:8720`                                      |

> 重复启动同一档会被识别并跳过（`[skip] the engine is ALREADY running`）。
> 控制台窗口可以留着不关（不占显存），下一次启动会复用。

## 5. 能力边界（先知道「不行」什么，省得白折腾）

| 能做                             | 不能做 / 不建议                                       |
| -------------------------------- | ----------------------------------------------------- |
| 纯文本对话、长材料问答、代码片段 | **多模态**（模型无视觉塔，不能看图）                  |
| 单用户、单路                     | **并发**（第二个请求会排队）                          |
| 离线、隐私安全                   | **联网 / 最新知识**（知识停在训练时）                 |
| 日常档 4k 输出、长档 8k 输出     | **超池题面**（不可信，必须分段/分片）                 |
| 结构化短回答、总结、改写         | **大量工具的 agent 循环**（上游 B17，工具调用不可靠） |

**一句话总结能力边界**：它是一个**离线、单路、纯文本、可信题面上限 12,800/51,200 token** 的本地助手；
把它当"小范围高可靠"用，别当"全能云端大模型"用。

## 6. 三种用法的标准姿势

### 6.1 纯文本对话

- 直接问，`max_tokens` 给 **1,024 ~ 2,048**；短回答给 256~512 更快。
- 多轮对话：客户端自己带历史，**别把几百轮历史一直拖下去**——超池后质量下降；长了就新开会话。

### 6.2 长材料问答（本机最需要注意的场景）

- **铁律**：题面 token + 输出 token ≤ 池（日常 12,800 / 长档 51,200）。
- 材料 ≤ 8,000 token：日常档直接贴，没问题。
- 材料 10,240 ~ 12,800：日常档能装但接近上限，**要求它引用原文**再核对。
- 材料 > 12,800：**换长档**；> 51,200：分片（见 §9）。
- **长材料放最后一条用户消息**，不要放在很长的历史里（网关 L1 会丢超大单条历史消息）。

### 6.3 代码工作

- 贴**相关文件片段**而不是整个仓库；一次问一个明确的问题。
- 让它改代码时，要求"**只输出完整文件 / 完整函数**"，并给 `max_tokens ≥ 2048`，防止写一半。
- 代码审查：分文件提问；让它先列问题清单再逐条展开。

## 7. 四个真实场景，照着做

### 场景 A：问一段代码（最常见）

````text
[system] 你是资深 Python 工程师。
[user] 解释这段代码做了什么，指出潜在 bug：
```python
<粘贴 50~200 行>
````

要求：先 3 行摘要，再逐条列 bug。

````

参数：日常档，`max_tokens=1024`，`temperature=0.2`。

### 场景 B：贴一份长材料，问一个问题（**最需要注意**）

```text
[user] 下面是一份文档，读完后回答最后的问题。
<材料（≤ 8,000 token 用日常档；更多用长档）>
问题：<一个明确的问题>
要求：回答时引用原文中的关键句子。
````

参数：材料小用日常档；大用长档（`max_tokens=2048~8192`；日常档 1024~2048）。超材料要分段。

### 场景 C：让它写一小段代码

```text
[user] 用 PowerShell 写一个脚本：<需求>。
要求：完整可运行，含错误处理；只输出代码，不要解释。
```

参数：`max_tokens=2048`，`temperature=0.2`；写一半停了先看 §12。

### 场景 D：贴一段报错

```text
[user] 这个报错怎么解决？（环境：Windows / PowerShell 5.1）
<报错原文>
```

参数：`max_tokens=512~1024`。

## 8. 客户端参数手册

| 参数                   | 建议                               | 说明                                                  |
| ---------------------- | ---------------------------------- | ----------------------------------------------------- |
| `model`                | **`j27b`**                         | 引擎只认这个 id（写别的名字 → 404）                   |
| `max_tokens`           | **显式给**：日常 ≤2048、长档 ≤8192 | 不写会用服务端默认（B37 会静默截断）                  |
| `temperature`          | 0 ~ 0.3（代码/事实）、0.7（闲聊）  | 越高越发散                                            |
| `top_p` / `top_k`      | 0.9 / 20（默认）                   | 不建议大改                                            |
| `stream`               | 可选                               | SSE 流式；`thinking off` 时只出正文                   |
| 超时                   | **≥300 秒**                        | 长档 8k 输出要 6~7 分钟                               |
| 并发                   | **1**                              | 不要并发，引擎单路                                    |
| `thinking` / reasoning | 默认关                             | 需要时用 `thinking_budget ≥1024`，并接受更慢/额度被吃 |

> **中文乱码**：上游 B36（响应头无 `charset=utf-8`）。客户端强制 UTF-8 解码即可。

## 9. 长材料的正确做法

### 9.1 那条核心规则 + 一个自检

> **规则：题面 token + 输出 token ≤ 池。**

自检：日志（或客户端 usage）里 `prompt` 是否 ≤ 池？响应有没有 `finish_reason=length`？
若日志出现 `prompt exceeds the resident Device KV pool` ⇒ 已经超池，**答案不可信**。

### 9.2 按材料规模选策略

| 材料规模        | 策略                                                              |
| --------------- | ----------------------------------------------------------------- |
| ≤ 8,000 token   | 日常档直接问                                                      |
| 8,000 ~ 12,800  | 日常档 + 要求引用原文；或换长档                                   |
| 12,800 ~ 51,200 | **长档**直接问（注意 TTFT 与输出耗时）                            |
| > 51,200        | **分片**：分段摘要 → 汇总；或用上游 `agg_gateway.py` 分片聚合网关 |

### 9.3 分块策略（手工版）

1. 按章节/空行切成 ≤ 8,000 token 的块（长档可 ≤ 40,000）。
2. 每块问同一个问题，得到"分块答案"。
3. 把分块答案（不是原文）汇总，再问一轮总问题。
4. 要求模型**标注引用块号**，便于你核对。

### 9.4 会话管理

- 长材料问答**不要拖多轮**：一轮问透，需要追问就新开一轮只带结论。
- 超过半小时的长会话建议新开（上下文只增不减，越用越慢）。

## 10. 代码工作专题

| 场景     | 做法                                        | 参数                                         |
| -------- | ------------------------------------------- | -------------------------------------------- |
| 读代码   | 贴相关函数 + 问"它做了什么/有什么风险"      | 日常档，`max_tokens 1024`，`temperature 0.2` |
| 写代码   | 需求写清楚 + 要求完整可运行；一次一个文件   | `max_tokens 1024~2048`                       |
| 代码审查 | 先要"问题清单"，再逐条展开                  | `max_tokens 2048`                            |
| 报错排查 | 贴报错 + 环境 + 已试过什么                  | `max_tokens 1024`                            |
| 重构     | 一次一个函数/文件，要求输出 diff 或完整文件 | `max_tokens 2048`                            |

**代码场景红线**：

- 不要让它"凭记忆补全"大段不存在的 API——本地模型知识停在训练时。
- 写一半停了 ⇒ 客户端显式 `max_tokens` + 题面+输出≤池（B35/B37）。
- 需要长输出时用**日常档**（63~72 tok/s），别在长档等 20 tok/s。

## 11. 在 DSH 里用本地模型

（DSH = DeepSeek Harness；以下为 v2 迁移后的配置口径，**需重启 DSH 生效**）

1. 先启动一个档：`21-launchers\start-daily.bat` 或 `start-long.bat`。
2. DSH **新开会话** → 模式选 **「本地小模型模式（8G·KV 流式）」**。
3. 模型按当前档选（两个 provider，模型 id 都是 `j27b`，靠预算区分）：
   - 日常档运行中 → **`j27b-daily`（ctx 10240 / out 2048）**，provider `NInfer Local (Daily 8G)`
   - 长档运行中 → **`j27b-long`（ctx 42496 / out 8192）**，provider `NInfer Local (Long-context 8G)`
4. **不要开旧会话**：旧会话记的是 v1 的模型/端口，v2 已经没有。
5. 验收看引擎日志：`req#N started | … | max output 2048|8192 | thinking off | tools N`；
   `prompt ≤ 10240`（日常）/`≤ 42496`（长档）。
6. 用完 `21-launchers\stop-daily.bat` 释放显存。

> **工具面**：本地模式 preset 只剩 5 个工具（pwsh + read/write/edit/read_image）。
> 实验性的 `dsh-experimental-agent-team-profile` 建议关掉——它会把工具面从 5 变多、prompt 变长，
> 而本地小模型的多工具调用不可靠（上游 B17）；关法：GUI → Plugins 页，热重载。

## 12. 新手最容易踩的坑

| 坑                           | 现象                             | 正确做法                         |
| ---------------------------- | -------------------------------- | -------------------------------- |
| 只看端口/`/v1/models` 判活   | 以为活了，发请求没反应           | 用 `healthcheck.bat`（真发请求） |
| 客户端不写 `max_tokens`      | 输出写一半就停（B37）            | 显式给 1024~2048（长档 8192）    |
| 贴了超大材料还问"看懂了吗"   | 答得很像但漏中间（超池）         | 题面+输出 ≤ 池；大了分段或换长档 |
| 把长材料放在很长的聊天历史里 | 模型说"没看到"（网关 L1 丢消息） | 材料放最后一条 user 消息         |
| 一边跑一边开游戏/录屏        | 启动失败（reservation）          | 先关占卡程序                     |
| 两个档同时开                 | 第二个起不来/端口冲突            | 直接双击另一个档脚本会自动切     |
| 并发发多个请求               | 后面的在排队，像卡死             | 一次一个                         |
| 用长档写代码                 | 等 20 tok/s 等很久               | 代码用日常档                     |
| 中文乱码                     | 客户端显示 `æ»å±æ`               | 按 UTF-8 解码（B36）             |
| 一直不换会话                 | 越来越慢、答得越来越飘           | 新开会话                         |
| 直接双击 `infer-serve.exe`   | `0xC0000135` 一闪而退            | 一律用 `启动器.bat` / 一键脚本   |

## 13. 安全、隐私、许可

- **完全离线**：引擎只监听 `127.0.0.1`，不上传任何数据；**不要把端口改成 `0.0.0.0` 或转发到公网**。
- **无鉴权**：API Key 随便填即可，但**别把带明文令牌的客户端配置提交到公开仓库**。
- **许可**：引擎/工具 Apache-2.0（上游仓），模型权重归其作者（详见 [10 · 许可与致谢](10-许可与致谢.md)）。
- 本方案涉及的脚本/配置不带任何凭据。

## 14. 术语表

| 术语                         | 一句话解释                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------- |
| **KV 缓存 / KV 池**          | 模型"记住上文"用的中间状态；池 = 显存里常驻的那部分（页 = 64 token）          |
| **KV 流式（KVMem 环）**      | 设备池可以比逻辑上下文小：放不下的页降到主机内存，需要时按内容检索搬回        |
| **host KV / 主机层**         | 内存里钉住的 KV 存储（3.25 GiB），不占显存                                    |
| **四桶预算**                 | `protect / skeleton / evidence / recent / free`；恒等式 `sum == pool`         |
| **逻辑窗口 `--max-context`** | 单序列可寻址的最大上下文（日常 131,072 / 长档 262,144）                       |
| **可信单题面**               | 题面 token ≤ 池（日常 12,800 / 长档 51,200）才可信                            |
| **MTP**                      | 模型自带的投机解码头；日常档 draft4 把 decode 从 36 提到 63~72 tok/s          |
| **网关让位阶梯**             | 8081 网关在请求前压缩：L0 直通 / L1 裁历史 / L2s 分段摘要 / L2 压缩 / L3 拒答 |
| **B33 / B35 / B36 / B37**    | 上游未修缺陷：429 / 输出静默截断 / 无 charset / 默认 max_tokens 截断          |
| **单路**                     | 同一时刻只服务一个请求（`--max-concurrency 1`）                               |

## 15. 迁移复盘：10 条可复用经验

> 从 v1 单 arch 引擎迁移到 v2 KV 流式两档，以及迁移后在实际使用中踩过的坑，压成 10 条。以后再换引擎/换客户端/换显卡，按这个走能少走弯路。

| # | 经验 | 一句话理由 |
|---|---|---|
| 1 | **先冻结基线再动手** | 旧套哈希、配置、备份先落盘；没有回滚点不迁移 |
| 2 | **真请求才算"活着"** | `/v1/models` 200 只证明端口活着，真发一句得到回答才是服务活着 |
| 3 | **参数全链路同源** | 引擎 profile、网关 headroom、客户端 contextWindow/maxTokens、预算闸门、selftest、文档必须同一个数；缺一处就"看着对但不生效" |
| 4 | **池是硬边界，逻辑窗不是可信窗** | 8 GB 上"题面 > 池"的答案不可信；131072/262144 只是引擎上限 |
| 5 | **8 GB 上每个 MB 都要算** | 权重+运行时+MTP 头是固定成本；`--no-cuda-graph`、host pageable 都是省出来的 |
| 6 | **上游默认值不可信** | 默认 medium 思考、MTP draft=1、cuda-graph、全局 max-context 都会拖慢或吃预算，要实测改写 |
| 7 | **先演练回滚** | v1 归档后先起 8095 真请求 OK，再开始用 v2 |
| 8 | **客户端与引擎解耦** | 引擎只认一个 model id；两档差异在服务端 profile 与客户端预算，不靠多个模型名 |
| 9 | **升级前后核对契约** | 客户端升级可能改提示词变量集合、重写配置、改端口；升级后先核对再用 |
| 10 | **变更连文档一起改 + 用测量闭环** | 改一次、量一次（峰值/解码/输出/TTFT），把读数写进文档；文档不同步会害下一个人按错预算使用 |

**一句话回顾**：冻结快照 → v1 归档 + v2 落位 → 两档实测定稿 → 一键脚本/验收工具 → 客户端双 provider → 文档与仓库 → MCP 可选 → 全量验收 + 回滚复演。

## 16. 常见问题 Q&A（迁移后新增）

**Q1：三个"上下文"数字到底看哪个？**
**池**是显存里真正驻留、可信的题面上限（日常 12,800 / 长档 51,200）；**逻辑窗**是引擎上限（131,072 / 262,144，超出池的部分靠主机层/检索，不等于可信）；**客户端有效预算** = 池 − 输出上限 − 512 slack（日常 **10,240** / 长档 **42,496**）。日常使用请按客户端预算，不是按逻辑窗。

**Q2：聊到超过客户端预算会怎么样？**
能继续，但会"忘事"：客户端先自动压缩旧对话；仍超出时网关会静默丢最老消息 / 压缩超大单条消息；极端情况（单条消息本身超预算）网关返回拒绝文本、不调用模型。重要结论请自己留档或新开会话。

**Q3：能主动压缩吗？**
可以：会话空闲时用客户端提供的压缩命令（DSH 里是 `/compact`），让当前模型把旧上下文压成摘要再继续。代价是一次模型调用（长档更慢），摘要有损；单条超大消息要先拆分。

**Q4：为什么日常回答写到 2,048 token 就停？**
v2.0.1 起日常档输出上限就是 2,048（用 2k 输出换 10,240 输入）。要长输出请切长档（8,192），或同时改客户端 `maxTokens`、引擎 `default_max_tokens`、网关 headroom 三处。

**Q5：模型名、两档、provider 怎么配对？**
引擎只认 `j27b` 一个 id（写别的 404）。先启动哪一档，客户端就选哪一档的 provider/预算：日常 `ctx 10240 / out 2048`；长档 `ctx 42496 / out 8192`。错配（日常引擎配长档预算）会越过 12,800 池触发 B35 静默截断。

**Q6：长材料怎么喂？**
硬规则：**题面 + 输出 ≤ 池**；接网关时还要 ≤ 客户端有效预算。小材料直接贴；接近上限就压缩/要求引用原文；超池就分块/分片或换长档；一次只问一个明确问题。

**Q7：429 / 卡住 / 超时怎么办？**
先用 `21-launchers\healthcheck.bat` 发真请求判活；429/长请求后卡死通常是上游 B33，重启对应档。超时设 ≥300 秒（长档 8k 输出要 6~7 分钟）。

**Q8：回答空白、半截、只有空 content？**
客户端必须显式给 `max_tokens`（B37 会静默截断）；输出上限别设太小；本机已关 thinking。长文要求分段并在每段结尾写标记。

**Q9：能把池调大吗？**
能，但不免费：池按显存公式（基座 + 页数×0.8357 MiB ≤ 7492 MiB 红线）算；越大 decode 越慢（历史上翻倍池 decode −38%），越容易踩碎片/429。真要提，一次 +32~64 页，实测峰值/解码后再决定。

**Q10：客户端升级后配置丢了/报 `{{cwd}}` 怎么办？**
先核对客户端补丁里的 provider/模型条目是否还在；`unknown prompt variable "{{cwd}}"` 是客户端新版本的提示词变量契约变了（只注册 provider/model）——删掉 persona 里的 `{{cwd}}` 行（或改固定文字）并重启客户端。升级后先新开会话验证一次。

**Q11：怎么安全回滚 v1？**
停 v2 → 启动 `90-legacy\v1-20261007\21-launchers\start-engine.bat`（8095）→ `healthcheck.bat` 真请求 OK → 用完 `stop-engine.bat`；客户端配置用迁移时的 `.bak` 覆盖并重启。回滚前先停 v2，避免端口/显存冲突。
