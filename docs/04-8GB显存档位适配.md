# 04 · 8 GB 档位适配（本方案的技术核心）

> 出厂参数在这张卡上**起不来**。这一篇讲清楚：**为什么起不来、改了哪几处、每处的代价是什么、
> 以及哪些"看起来该改"的地方我们刻意没动。**

---

## 1. 为什么出厂参数装不下

8 GB 显存要同时容纳三样东西：

| 项         | 大小          | 说明                                         |
| ---------- | ------------- | -------------------------------------------- |
| 模型权重   | **5.94 GiB**  | 三进制量化的实际占用                         |
| 引擎运行时 | **457.6 MiB** | KV 池结构 + 工作区（引擎自己报的 `runtime`） |
| 余量       | **560.0 MiB** | 引擎报告的 `free`                            |

而**出厂参数**里还有两项会额外吃显存：

| 出厂设置               | 后果                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| `--max-context 262144` | KV 缓存按上下文长度增长，262k 的 KV 远超 8 GB                    |
| CUDA Graph 预留        | 为加速而预留一大块显存 —— **在 8 GB 卡上这是压死骆驼的那根稻草** |

> **结论：这不是引擎缺陷，是"档位不适配"。** 换档位（参数）即可，不需要换引擎或重编译。

---

## 2. 必要改动清单（缺一不可）

### 2.1 容量类

| 参数                          | 出厂     | 本方案     | 依据                                | 代价                           |
| ----------------------------- | -------- | ---------- | ----------------------------------- | ------------------------------ |
| `--max-context`               | 262,144  | **65,536** | KV 显存随上下文线性增长             | 上下文变成 1/4（仍够长文材料） |
| `--kv-capacity`（设备 KV 池） | 出厂更大 | **4,032**  | 8 GB 卡的实测平衡点                 | 见 §3 的负结果                 |
| `--host-kv-mib`（主机层）     | 16,384   | **4,096**  | 主机层钉在内存里，按 32 GB 机器取值 | 超池时能挪去内存的 KV 变少     |

**实测容量行（判据）**：

```text
INFO capacity | KV 4,032 tokens, k8v4, explicit | pages 63/1,024 | runtime 457.6 MiB | free 560.0 MiB
```

> 1 页 = 64 token ⇒ 4,032 token = 63 页（另有 1 页用于索引，总容量 1,024 页）。

### 2.2 显存杠杆（决定"能不能起来"）

| 参数               | 出厂 | 本方案 | 作用                        |
| ------------------ | ---- | ------ | --------------------------- |
| `--gdn-state-fp16` | 关   | **开** | 状态张量用 fp16，直接省显存 |
| `--no-cuda-graph`  | 关   | **开** | 不预留 CUDA Graph 那块显存  |

**关于 `--no-cuda-graph` 的速度代价：实测为 0。**

| 配置                          | 解码速度                      |
| ----------------------------- | ----------------------------- |
| 不用 CUDA Graph               | **217.2 token/s**（本次测量） |
| 用 CUDA Graph（上游读数区间） | 196.8 ~ 237.9 token/s         |

上面的数字**落在区间内**，说明在这张卡上关掉 CUDA Graph 没有可测的性能损失。
（上游也把 `--no-cuda-graph` 列为部分 WDDM/驱动组合上的**必需项**。）

### 2.3 安全红线（这一条不设会崩）

| 参数                   | 出厂   | 本方案    | 为什么                                   |
| ---------------------- | ------ | --------- | ---------------------------------------- |
| `--default-max-tokens` | 32,768 | **2,048** | **客户端输出额度必须 ≤ 设备池 token 数** |

上游账本里最危险的一条缺陷：

> **超池题面 + 大输出额度 ⇒ worker 崩溃 ⇒ 此后该实例所有请求 503。**

出厂默认 32,768，是设备池（4,032）的 **8 倍**——这在本机就是**必崩配方**。
把它压到 **2,048**，同时约定客户端**硬上限 4,032**。

### 2.4 稳定性止血（零编译，出厂启动器没用过）

引擎自带两个开关，但出厂启动器**从来没有用过**：

| 开关                           | 作用                                       |
| ------------------------------ | ------------------------------------------ |
| `--recover-invariant-failures` | 不变量校验失败时尝试恢复，而不是留下僵尸态 |
| `--kv-lease-growth`            | 输出租约按需增长，缓解"租约拿不到页"       |

它们是**零编译的止血手段**：不改引擎、不改参数语义，只把引擎里已有的能力打开。

### 2.5 六个环境变量（缺一不可）

```bat
set "NINFER_KV_WINDOW=16384"
set "NINFER_KV_RETRIEVE=8192"
set "NINFER_KV_RING=1"
set "NINFER_HOST_PAGEABLE=1"
set "NINFER_KV_REUSE_HOSTBACKED=1"
set "NINFER_TERNARY_PTQ1_FAST=1"
```

> ⚠️ **`NINFER_KV_RETRIEVE` 不能删**：上游记录过去掉它会让检索**静默答错**（不报错、答案变差）。
> ⚠️ 这六个是"环"的工作前提，**必须同时成立**。

## 3. 【负结果】池调大反而变慢（已实测并回退）

**动机**：设备池 4,032 太小，超池就不可靠。按常识"池越大越好"，于是试了 **8,192**。

**实测（计数语料 1,000 in / 1,000 out，三次复测）**：

| 指标                 | 池 4,032（基准） | 池 8,192             | 变化     |
| -------------------- | ---------------- | -------------------- | -------- |
| 解码                 | **72.2 token/s** | 44.8 / 43.8 / 45.5   | **−38%** |
| 整轮总耗时           | **15.6 s**       | 24.8 / 23.8 / 22.2 s | **+50%** |
| 冷启动 TTFT          | **1,733 ms**     | 2,486 ms             | **+43%** |
| 正确性（`7*5`/`+2`） | 通过             | 通过                 | 无差异   |
| MTP 接受             | 779/879          | 779/879              | 无差异   |
| 复用命中             | 99.6%            | 99.6%                | 无差异   |

**结论**：**纯粹的负优化**，已回退；实验用的启动器已删除。

**为什么与上游文档相反（诚实分析）**：上游那组"池大更好"的对照
（152 页 → 154 ms；640 页 → 118 ms）取自**另一台机（RTX 4080 SUPER）+ 另一种形状**，
而且比的是"40k 提示**第二轮**的 TTFT"，**不是短提示的解码吞吐**。
本机 8 GB + 短提示场景下，池变大 ⇒ 每个 token 要过更多常驻页与掩码 ⇒ 解码反而变慢。

> **这也是本仓库最想传递的一条方法论：实测 > 文档，但只在同一形态、同一口径下比较。**

## 4. 刻意"没改"的地方（以及为什么）

| 项                                          | 决定               | 理由                                                       |
| ------------------------------------------- | ------------------ | ---------------------------------------------------------- |
| `NINFER_KV_WINDOW`                          | **保持厂值 16384** | 改了要重验，而当前形态下没有收益证据                       |
| `NINFER_KV_RETRIEVE`                        | **保持厂值 8192**  | 上游警告：动它会让检索静默答错                             |
| 其它 17 个 `--kvmem-*` 开关 + 39 个环境变量 | **不动**           | 上游口径："其余别动"；且没有本机验证的场景                 |
| `--max-shared-prefixes 0`                   | **保持**           | 防止"逐字节重发超池题面"把引擎打砖                         |
| `--max-concurrency 1`                       | **保持**           | 引擎本身要求单路，>1 会被硬拒                              |
| `--kv-dtype k8v4`                           | **保持**           | 其它 dtype（fp8 / rk8v4 / int8）是上游**禁止项**；其余未验 |
| 比 4,032 **更小**的池                       | **不试**           | 上游明文："没测过、别压"                                   |

## 5. 还没做的调优项（诚实清单）

这些**没有做**，不是遗漏，而是缺场景或属研究级：

| 项                              | 为什么没做                                                        |
| ------------------------------- | ----------------------------------------------------------------- |
| `--draft-tokens` 扫 3/4/5       | 上游标【未验】；本机 4 已稳定（接受率 88.6%），换值需重跑全套判据 |
| `--adaptive-mtp`                | 上游标【未测】，且注明"要试先问作者"                              |
| 其它 `--kv-dtype`               | 除禁止项外均未验                                                  |
| 比 4,032 更小的池               | 上游明文禁止乱压                                                  |
| 40k 级超长针测                  | 需要 >10k 题面 + 超池多针夹具；属研究级，且夹具未随包分发         |
| 小池负控（把检索窗口改回 256）  | 同上，属研究级                                                    |
| 平台层护栏（防 agent 循环退化） | 需要写代码，且只在"长期跑 agent 循环"时才有必要                   |

**还有一个备而未用的杠杆**：`--prefill-chunk 256`（见 [07 · 排错手册](07-排错手册.md)）。
本机用 1024 没有撞到相关坑，所以没启用。

## 6. 最终生效的完整参数（可照抄）

```bat
set "NINFER_KV_WINDOW=16384"
set "NINFER_KV_RETRIEVE=8192"
set "NINFER_KV_RING=1"
set "NINFER_HOST_PAGEABLE=1"
set "NINFER_KV_REUSE_HOSTBACKED=1"
set "NINFER_TERNARY_PTQ1_FAST=1"

ninfer-serve-89.exe "<模型件路径>" ^
  --host 127.0.0.1 --port 8095 --model-id qwen3.8-27b ^
  --max-context 65536 --kv-capacity 4032 --kv-dtype k8v4 --host-kv-mib 4096 ^
  --prefill-chunk 1024 --spec mtp --draft-tokens 4 ^
  --default-max-tokens 2048 --default-reasoning-effort none --max-concurrency 1 ^
  --max-shared-prefixes 0 --gdn-state-fp16 --no-cuda-graph ^
  --recover-invariant-failures --kv-lease-growth ^
  --presence-penalty 0 --temperature 0.7 --top-p 0.9 --top-k 20
```

**逐项解释**见 [11 · 脚本与工具说明](11-脚本与工具说明.md)。

---

## 7. 一句话总结

> **在 8 GB 卡上，能不能跑取决于两个显存杠杆（`--gdn-state-fp16` + `--no-cuda-graph`），
> 会不会崩取决于一条红线（`max_tokens ≤ 池`），能不能省心取决于两个止血开关——
> 而"跑得更快"这件事，试过调大池，结论是别调。**
