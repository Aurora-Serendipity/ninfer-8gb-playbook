# 06 · KV 流式与长上下文机制

> 这一篇解释"为什么设备池可以比逻辑窗口小得多"、"为什么同一会话第二轮会秒回"、
> "为什么材料太长时答案会静默漏掉中间"，以及**日志里那几百行重复的行到底在说什么**。
>
> 本方案在 8 GB 卡上的两个档位，就是围绕这里的机制做的一次显式取舍。

---

## 1. 三层结构

```text
              ┌──────────────────────────────────────────────┐
   显存       │  设备 KV 池（日常 12,800 / 长档 51,200 token） │  ← 常驻，最快；可信单题面上限
              └──────────────────────────────────────────────┘
                               ↕ 降级 / 按需取回
              ┌──────────────────────────────────────────────┐
   内存       │  主机 KV 存储 3.25 GiB 钉住 + 会话状态 1.15 GiB │  ← 放不下的页降到这里
              └──────────────────────────────────────────────┘
                               ↕
              ┌──────────────────────────────────────────────┐
   逻辑窗口   │  --max-context 131,072 / 262,144 token        │  ← 单序列可寻址的最大上下文
              └──────────────────────────────────────────────┘
```

| 概念         | 实测值                                             | 说明                                 |
| ------------ | -------------------------------------------------- | ------------------------------------ |
| 页（page）   | **1 页 = 64 token**                                | 换页、降级、打分的最小单位           |
| 设备 KV 池   | 日常 12,800 = **200 页**；长档 51,200 = **800 页** | 显存里常驻的部分                     |
| 页表容量     | 日常 2,048 页；长档 4,096 页                       | 逻辑页上限（= `--max-context` / 64） |
| 主机 KV 存储 | **3.25 GiB**（钉在内存）                           | `host KV pinned`；不占显存           |
| 会话状态     | **1.15 GiB**（钉在内存）                           | `host state pinned`                  |

> **关键认知**：逻辑窗口（131k / 262k）只是"可寻址范围"，**不等于全部 KV 都常驻显存**。
> 设备池才是常驻区；超池的请求要靠"降级到主机 + 按内容检索取回"来续命，
> 而这条链路的可靠性有明确边界（见 §7）。

---

## 2. 四桶预算：池里的页怎么分

引擎每轮把设备池的页分到几个**桶**里，并强制一条恒等式：

| 桶         | 放什么                                 | 作用                                     |
| ---------- | -------------------------------------- | ---------------------------------------- |
| `protect`  | sink ∪ 头部段（`first_hidden` 可自证） | 保住题面开头的事实，检索预算不足时也不丢 |
| `skeleton` | 结构骨架（长材料分段后的"目录/框架"）  | 让检索有稳定的锚点                       |
| `evidence` | 按内容相关性打分后取回的页             | 回答当前问题真正需要的证据               |
| `recent`   | 最近窗口（对话尾部）                   | 多轮连续性的保证                         |
| `free`     | 未分配                                 | 给新 token / 输出租约用                  |

**恒等式**：`protect + skeleton + evidence + recent + free == pool`，违反即**硬抛**（不是"看起来没崩"）。
启动后日志会打一行 `[ring] budgets … sum==pool: yes`——**这是可判据的自证，不是装饰**。

## 3. 降级、检索与主机层

1. **降级**：设备池装不下的旧页被降到主机 KV 存储（`host_kv_arena`；需要 env `NINFER_HOST_PAGEABLE=1`，否则为 `null`、整环退化成 dense）。
2. **检索**：新一轮请求到来时，用**当前查询**给主机层里的页打分（content scoring），把高分页搬回设备池（H2D）。
3. **组装**：搬回的页 + `protect` 头部 + `recent` 尾部一起组装成这一轮的注意力窗口。

**日志证据（实测）**：

```text
[ninfer] ring retrieve: which=text preferred=… restored=… …
kvmem_score: SELECT … kept=512 scored_kept=448 candidates=560 …
[ninfer] mask hidden: … mid_hidden=… …
```

长档实测检索预算：**budget 512 页，sink 64，scored_kept 448**。
这些行每处理一个 1,024 token 的预填块就打一遍，所以长题面日志会"刷屏"——**正常**。

---

## 4. 前缀复用（"第二轮秒回"的原理）

同一个会话里，前面内容的 KV 不必重算：环把它们的检查点留在主机层，
下一轮直接 **adopt（复用）**，`cached_tokens` 不回落。

| 实测                       | 日常档                                                |
| -------------------------- | ----------------------------------------------------- |
| `7*5` → `35` 之后追问 `+2` | 第二轮 `cache 27`（本轮新增 27 token），TTFT 明显下降 |
| 复用生效的判据             | `cached_tokens > 0` 且 TTFT 下降；**不是**某一行日志  |

> `publish host-backed:` 与 `adopt host-backed:` 两行**不能单独当复用证据**：
> 前者是无条件行为，后者只说明"采纳了主机层"。

## 5. MTP 投机（日常档为什么快）

日常档开 `--spec mtp --draft-tokens 4 --mtp-attention-window 8`：模型自带的 MTP 头先猜 4 个 token，
主模型一次校验。日志自证：

```text
[spec] backend=mtp draft_tokens=4 attention_window=8 ngram=15
```

| 配置                  | decode（本机实测）    |
| --------------------- | --------------------- |
| draft=1（出厂）       | 36 ~ 37 tok/s         |
| **draft=4（本方案）** | **63.3 ~ 71.6 tok/s** |

接受率 **77 ~ 99%** 视任务；显存不变。长档为了换窗口**不开 MTP**（`backend=none`），decode 约 20 tok/s。

## 6. 网关让位阶梯（L0 / L1 / L2s / L2 / L3）

网关（`gateway\chat_gateway.py`，8081）在请求到达引擎**之前**先压缩，避免"题面 + 输出 > 池"：

| 级      | 动作     | 说明                                                                                                                                                                         |
| ------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L0**  | 直通     | `est ≤ pool_usable`（= 池 − headroom）时原样转发                                                                                                                             |
| **L1**  | 裁历史   | 丢弃最旧的非 system 消息（**system 与最后一条 user 永不丢**）                                                                                                                |
| **L2s** | 分段注入 | 当**单条消息**过大时：按结构单元切成 ≤0.7×usable 的段，逐段摘要后回注（摘要走引擎自己的请求）                                                                                |
| **L2**  | 就地压缩 | 对最大的一条 user/tool 消息保留头 10% + 尾 10% + 与最后一条 user 消息 n-gram 重叠最高的段落块，并插入可见标记行；还有 L2b（反复减半）/L2c（压缩 system）/L2z（强制重建）兜底 |
| **L3**  | 诚实拒答 | 压缩仍不可行时返回 **HTTP 200** + 一段正常的助手文本说明超限（不是 500）                                                                                                     |

**估算法**：`est_tokens = ceil(utf8_bytes / 3.6)`（中英混合保守估计）。

**硬规则**：

- `stream:true` 的 SSE **原样透传**；
- `tools` / `tool_calls` **永不删除**；
- 不改引擎侧任何选项。

**headroom 与预算**：`pool_usable = 池 − gateway_headroom`；本方案 headroom = 输出上限 + 512：
日常 `12,800 − 2,560 = 10,240`、长档 `51,200 − 8,704 = 42,496`。
这两个数就是客户端推荐的 `contextWindow`（见 [09](09-第三方客户端接入.md)）。

> ⚠️ **网关让位是有损的，而且 L1 会丢材料**：实测一条 17,701（est）的超大单条历史消息
> 被 L1 直接丢弃，模型诚实回答"我没有访问任何密码"——**诚实，但材料已经没了**。
> 长材料请放在**最后一条用户消息**里（走 L2/L2s），或直接用长档 / 分片网关。

## 7. 超池时会发生什么

1. 引擎打告警：

```text
[warning] … prompt exceeds the resident Device KV pool: prompt N tokens (… pages) > pool M tokens (… pages).
          Part of the prompt is therefore not resident, and the MIDDLE of such a prompt has been measured
          to go missing with no error line, HTTP 200 and a plausible wrong answer; the root cause is not localized.
```

2. 检索接手：把相关页从主机层搬回设备池（**所以不一定出错**）。
3. 但**中段有静默丢失的实测记录** ⇒ **这条请求的答案不能当作"它读过了全文"**。

**实用判据（以池为界，不以逻辑窗口为界）**：

| 材料规模（日常档）                      | 可靠性             | 做法                                                                     |
| --------------------------------------- | ------------------ | ------------------------------------------------------------------------ |
| ≤ 10,240 token（题面 + 输出仍 ≤ 12,800） | 最高（全在设备池） | 直接贴、直接问                                                           |
| 10,240 ~ 12,800                          | 中（接近池上限）   | 缩短材料 / 明确要求引用原文                                              |
| > 12,800                                | 低（超池）         | **换长档**（池 51,200）或分片（上游 `agg_gateway.py`）或让网关让位后核对 |
| > 51,200（长档也超池）                  | 不适合单请求       | 必须分片；每片 ≤ 池                                                      |

> **"没打警告"不等于安全**：告警只在引擎认为超池时打，边界口径以上游为准。

## 8. 日志怎么读（只看这几行就够）

| 行                                                                                    | 含义                                       | 危险吗                                     |
| ------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| `engine ready …`                                                                      | 引擎就绪（权重加载 + device profile 完成） | 否                                         |
| `capacity \| KV <pool> tokens, <dtype>, explicit \| pages …/… \| runtime … \| free …` | 池自证；**与档位对照**                     | 否（不符才危险）                           |
| `host KV pinned \| 3.25 GiB` / `context cache \| host 8 states, 3.25 GiB KV`          | 主机层生效                                 | 否（**缺了危险**）                         |
| `[ring] host_kv_arena is null … run dense`                                            | 主机层失效                                 | ✅ **是**（检查 `NINFER_HOST_PAGEABLE=1`） |
| `[ring] budgets … sum==pool: yes`                                                     | 四桶恒等式                                 | 否                                         |
| `[spec] backend=mtp draft_tokens=4 attention_window=8 ngram=15`                       | 投机自证                                   | 否                                         |
| `req#N started \| … \| max output 2048\|8192 \| thinking off \| tools N`              | 请求开始；**核对 thinking off 与输出上限** | 否                                         |
| `req#N done \| … \| prompt N …`                                                       | 请求结束（权威读数）                       | 否                                         |
| `kvmem_score: SELECT …` / `ring retrieve: …`                                          | 检索在动                                   | 否（长题面刷屏正常）                       |
| `prompt exceeds the resident Device KV pool …`                                        | **超池**                                   | ✅ **是**                                  |
| `Paged KV pool has no free page for host-restore`                                     | **B33 的 429 报文**                        | ✅✅ **是**（重启引擎）                    |
| `queue N ms`                                                                          | 单路排队                                   | 否                                         |

更完整的"症状 → 处置"见 [07 · 排错手册](07-排错手册.md)。

## 9. 一句话总结

> **设备池是"桌面"，主机 KV 是"书柜"，内容打分是"按你现在问的那句话去书柜里找书"。
> 找书要时间（长档 48k 题面 TTFT 79 秒），桌面太小（超池）时答案就不可信。
> 网关则在门口先帮你把材料剪短——但它剪掉的东西不会还给你。**
